# Feature Specification: Agents Section of the Web Console

**Feature Branch**: `005-web-delegate-agents`

**Created**: 2026-11-19

**Status**: Draft

**Input**: User description: "Agents section of the web console. The Agents entry in the sidebar, a placeholder today, becomes the place where an operator manages the delegate agents Freyja may hand work to, without editing environment variables or restarting the service. It shows every configured agent as a card: its name, whether messages to it need a person's approval or run without one, whether it could be reached when last tried and when, the error if it could not, and what the agent says of itself on its card (name, description, version, skills). An Add button opens a form with a name, an address on this machine, and the approval choice, which defaults to requiring approval. The operator can add an agent, change its address or its approval choice, remove it, and check it, which reads the agent's card again and reports whether it can be used. Adding or changing an agent reads its card first: an agent whose card cannot be read, requires authentication, accepts no text, offers no usable interface, is not on this machine, or whose name is taken by another agent or a tool server is refused with the reason, and nothing is saved. A change takes effect on the running service without a restart: runs already in progress finish with the agents they started with, and the next run has the new set. The agents configured through FREYJA_A2A_AGENTS today appear as read-only entries marked as coming from the environment and keep working unchanged, so an existing deployment behaves as before; a saved agent may not take the name of one of them. Saved agents live in the service's database, survive a restart, and are the same for every service instance sharing the database. An agent that cannot be reached when the service starts does not stop the service: it is shown as unreachable, and hand-offs to it fail as they do today for an agent that stops answering. The approval choice is the only thing that decides whether a message to an agent pauses for a decision, exactly as today, on the orchestrator and on its subagent and in background runs; switching an agent to run without approval removes the human check on everything sent to it, so the console asks for confirmation and says so. Removing an agent, or changing its address, while it has tasks still pending gives those tasks up, as happens today when an agent is removed from the configuration, and the confirmation says how many there are. The address an operator entered is shown back to them in the Agents section so they can check and change it; it is still kept out of everything the orchestrator sees and out of every thread, log line, and catalog entry. Out of scope: tool servers reached over MCP, which stay configured through the environment; agents on another machine; agents that need credentials; authentication for the console or the API; a different set of agents per thread; and renaming a saved agent, since its name is part of its tools' names and of every conversation already held with it. The web app stays a client of Freyja's API only, and the API stays unauthenticated and bound to this machine."

## Clarifications

### Session 2026-11-19

- Q: When an agent named in `FREYJA_A2A_AGENTS` is down at startup, or its card cannot be used, should the service start anyway? → A: Yes, with warnings in the log and in the console. One rule for saved and environment agents: the service starts and logs a warning naming each agent it cannot use and why. The console warns too, about every agent that is down, at startup or later: on the agent's own card, in a warning above the cards that names each such agent, and on the Agents entry of the sidebar, where it shows from every section. An invalid entry still stops startup.
- Q: A run is in progress and started while an agent ran without approval; the agent is then switched to require approval, or removed. May that run still send it messages nobody has seen? → A: No, in both cases. From the moment the change is answered, a run in progress sends nothing unseen to an agent that now requires approval or was removed: the call gives an error result and the run continues. The run keeps its tools and, for a moved agent, the earlier address.
- Q: A hand-off waits for a decision; before it is decided its agent is moved, or removed and added again under the same name. If it is then approved, is the message sent to the agent now holding the name? → A: After a move only. A moved agent is the same agent, so an approved proposal goes to its current address. An agent removed and added again is a different agent: the earlier proposal is never sent, whatever the decision.
- Q: The spec has two rules the description did not ask for: an address that already belongs to another agent cannot be saved, and the console cannot be shown inside a page of another origin. Which stay in this feature? → A: Both. Each closes a way around the approval choice that a confirmation alone does not.
- Q: When only a saved agent's approval choice is changed, is its card read first, with the change refused when the card cannot be read? → A: No. A change of the approval choice alone never contacts the agent and is never refused because of the agent's state, in either direction. A change of address reads the card first.

### Amended by feature 010, 2026-11-26

- FR-022's approval choice is now named an agent's own mode, Manual or Auto, and it decides
  together with the instance's agents' approval mode: a message runs without approval only
  when both are Auto (010 FR-003). Setting that mode to Manual holds at once, as a switch to
  requiring approval does, by the same check before a send (010 FR-004).

## User Scenarios & Testing *(mandatory)*

Four terms are used throughout. An **environment agent** is one named in `FREYJA_A2A_AGENTS`; a **saved agent** is one an operator added through the console. An agent's **approval choice** is one of two: messages to it **require approval**, or they **run without approval**. To **move** an agent is to change a saved agent's address.

### User Story 1 - See which agents Freyja can hand work to (Priority: P1)

An operator opens the Agents section. Every configured agent is a card: its name, its approval choice, whether it could be reached when last tried and when, the error if it could not, and what the agent says of itself on its card: its name, description, version, and skills. On a deployment that has only ever been configured through environment variables, each agent named there has a card marked as coming from the environment, with nothing to change or remove. With no agent configured, the page says so.

**Why this priority**: It replaces the placeholder with the smallest slice that is useful by itself: an operator can see, without reading configuration or the catalog's raw answer, which agents the orchestrator may hand work to and which of them run without a person's approval. Every other story adds to this page.

**Independent Test**: Start the service with two environment agents, one requiring approval and one not, and no saved agent, then open the Agents section. It shows two cards with the right approval choice, reachability, and card details, each marked as coming from the environment and with no control to change or remove it. Neither agent's address is on the page or in what the page received. A run that hands off to each behaves exactly as it did before this feature.

**Acceptance Scenarios**:

1. **Given** a service with environment agents and no saved agent, **When** the operator opens the Agents section, **Then** it shows one card per agent with its name, its approval choice, whether it was reachable when last tried and when, and the name, description, version, and skills from its card, marked as coming from the environment, with no control to change or remove it.
2. **Given** an agent whose most recent use failed, **When** its card is shown, **Then** it is marked with a warning and says the agent could not be reached, when that was, and why, and the reason holds no address.
3. **Given** no agent is configured, in the environment or saved, **When** the operator opens the Agents section, **Then** the page says that no agent is configured.
4. **Given** the service cannot be reached, **When** the operator opens the Agents section, **Then** the page says so and offers to try again, and it shows no agent as if it were current.
5. **Given** an agent whose card text contains markup or a link, **When** its card is shown, **Then** the text appears as plain text: nothing in it is rendered as markup, loaded, or followed.
6. **Given** an environment agent, **When** its card is shown, **Then** its address appears nowhere on the page or in what the page received.
7. **Given** the Agents section is opened or read again, **When** the service answers, **Then** no agent was contacted because of it.
8. **Given** a service configured through the environment only, with every agent answering, **When** runs hand work to its agents, **Then** hand-offs, pauses, pending tasks, and the catalog behave as they did before this feature.

### User Story 2 - Add an agent and hand work to it without a restart (Priority: P2)

The operator presses Add and fills in a name, the agent's address on this machine, and the approval choice, which is already set to requiring approval. The service reads the agent's card first. If the agent can be used, it is saved and appears as a new card, and the next run can hand work to it: the service was not restarted and no environment variable was touched. If it cannot be used, the form says why and nothing is saved. After a restart the agent is still there.

**Why this priority**: This is the reason for the feature. Adding an agent today means editing a variable and restarting the service, which interrupts every run in progress and stops the service outright if the new agent happens to be down.

**Independent Test**: With the service running, start the stand-in agent, add it through the console, and send a message that leads to a hand-off to it. The run pauses for a decision, since approval is required by default; approve it and confirm from the stand-in's side that it received exactly that message. Restart the service: the agent is still listed and still usable. Try to add an agent at an address where nothing listens, and one whose name is already used: each is refused with its reason and no card appears.

**Acceptance Scenarios**:

1. **Given** the Agents section, **When** the operator presses Add, **Then** a form opens with a name, an address, and the approval choice set to requiring approval, and with nothing left from an earlier use of the form.
2. **Given** the form with a free name and the address of an agent that can be used, **When** the operator saves, **Then** a new card appears with the name, the address in the form the service keeps it in, the approval choice, the agent as reachable, and its card's details.
3. **Given** an agent was just added, **When** a run starts on the same service, **Then** the orchestrator and its subagent have that agent's hand-off and cancel tools, a hand-off reaches the agent under its approval choice, and the service was not restarted.
4. **Given** a run is in progress, **When** an agent is added, **Then** that run finishes without the new agent, and the next run on the same thread has it.
5. **Given** the form, **When** the address is one where no card can be read, or the card requires authentication, accepts no text, or offers no interface Freyja speaks, **Then** nothing is saved and the form says which of these it was, keeping what was typed.
6. **Given** the form, **When** the name is already an agent's, saved or from the environment, or a tool server's, or one of the agent's two tool names is already another tool's, **Then** nothing is saved and the form says so at the name.
7. **Given** the form, **When** the name is not in the allowed form, or the address is not a web address on this machine, carries a user name, a password, a query, or a fragment, or is already another agent's, **Then** nothing is saved and the form names the value and the rule.
8. **Given** a saved agent, **When** the service restarts, **Then** the agent is still listed with the same name, address, and approval choice, and runs can hand work to it.
9. **Given** several service instances share one database, **When** an agent is added through one of them, **Then** a run that starts on any instance after the add was answered has it.
10. **Given** the form with the approval choice set to running without approval, **When** the operator saves, **Then** the console asks for confirmation, saying that nothing sent to this agent will be seen by a person first, and no request that changes anything is sent before they confirm.
11. **Given** an agent is added or refused, **When** the agent's own record of what it received is read, **Then** it holds no message and no task: only its card was read.
12. **Given** an agent was just added, **When** the catalog is read, **Then** it lists the agent and its tools with the classification its approval choice implies, and no address.

### User Story 3 - An agent that is down does not stop the service (Priority: P3)

An agent is not running when the service starts, or its card can no longer be used. The service starts anyway. The agent's card in the console says it could not be reached, when, and why. A hand-off to it fails with an error the orchestrator reports, as it does today for an agent that stops answering, and works again once the agent answers, with no restart. At any time the operator presses Check on a card: the service reads the agent's card again and the console says whether the agent can be used.

**Why this priority**: Once agents are saved in the database, one of them being down must not keep the whole service, and with it the console that could fix or remove the agent, from starting. It comes right after adding because adding is not safe to rely on without it.

**Independent Test**: Add the stand-in agent, stop it, and restart the service. The service starts; the agent's card says it could not be reached and gives the reason. Press Check: the console reports that the agent cannot be used. A run that hands off to it gets an error result and continues. Start the stand-in again and press Check: the console reports that it can be used, and the next hand-off succeeds. The service was never restarted after the first time. Repeat with an environment agent that is down at startup.

**Acceptance Scenarios**:

1. **Given** a saved agent that is not answering, **When** the service starts, **Then** it starts and serves requests, its log has a warning naming the agent and the reason, the agent is listed as unreachable with the reason and the time, its card's details are those kept with it, and every other agent works.
2. **Given** an environment agent whose card cannot be read, or whose card requires authentication, accepts no text, or offers no interface Freyja speaks, **When** the service starts, **Then** it starts and serves requests, its log has a warning naming the agent and the reason, and that agent is listed as unreachable with the reason.
3. **Given** an environment entry that is itself invalid: a name not in the allowed form, an address that is not on this machine, a setting the configuration does not define, a name shared with a tool server, or a tool name already taken, **When** the service starts, **Then** startup fails naming the agent, as it does today.
4. **Given** an agent listed as unreachable, **When** a run hands work to it, **Then** the orchestrator gets an error result naming the agent, the run continues, and nothing is retried, as today.
5. **Given** an agent that was down when the service started and is answering again, **When** a run hands work to it, **Then** the hand-off succeeds without a restart or any action by the operator, and its card says it is reachable.
6. **Given** any agent's card, saved or from the environment, **When** the operator presses Check and the agent can be used, **Then** the console says so, and the card shows it as reachable, the time of the check, and the card details just read; when those differ from the details kept before, the console says that the agent's card changed.
7. **Given** any agent's card, **When** the operator presses Check and the agent cannot be used, **Then** the console says why, the card shows it as unreachable with that reason and the time, and the agent stays configured as it was.
8. **Given** an agent that does not answer at all, **When** it is checked, **Then** the check ends within twenty seconds and reports that the agent did not answer in time.
9. **Given** a check, **When** it ends, **Then** the agent received no message and no task, and no thread, pending task, address, or approval choice changed.
10. **Given** one or more agents are listed as unreachable or not in use, **When** the operator opens the Agents section, **Then** a warning above the cards names each of them, and each one's card is marked with a warning and gives the reason; with every agent reachable there is no warning.
11. **Given** one or more agents are listed as unreachable or not in use, **When** the operator opens the console on any section, the LLM section included, **Then** the Agents entry of the sidebar carries a warning that says how many agents cannot be used.
12. **Given** the console warns about an agent, **When** the agent answers again and the list is next read, after a check or otherwise, **Then** the warnings about it are gone from its card, from above the cards, and from the sidebar.
13. **Given** an agent with tasks pending, **When** the service starts while the agent is down, **Then** the tasks stay pending, and once the agent answers again they are checked as today, without a hand-off or a check by the operator having to come first.

### User Story 4 - Decide whether messages to an agent need a person's approval (Priority: P4)

The operator opens a saved agent and changes its approval choice. Switching it to run without approval removes the human check on everything Freyja sends to that agent, so the console asks first and says exactly that. After they confirm, hand-offs to the agent no longer pause, from the next run. Switching back to requiring approval is confirmed too and holds at once: from that moment nothing reaches the agent without a person's decision, not even from a run that was already under way.

**Why this priority**: The approval choice is the one setting here that touches the rule the constitution makes non-negotiable. It deserves its own story so that its confirmation, its effect on every kind of run, and its edges are specified and tested by themselves.

**Independent Test**: Add the stand-in agent requiring approval. A hand-off pauses. Switch the agent to run without approval: the console asks and names what is being given up; cancel, and a hand-off still pauses. Switch and confirm: the next run's hand-off reaches the stand-in with no pause, directly, through the subagent, and in a background run. Start a run that will hand off twice with a wait between, switch back and confirm during the wait: the second hand-off is not sent. The next run pauses again.

**Acceptance Scenarios**:

1. **Given** a saved agent that requires approval, **When** the orchestrator, its subagent, or a background run proposes a hand-off, a follow-up, an answer, or a cancel to it, **Then** the run pauses before anything is sent, as today.
2. **Given** a saved agent that requires approval, **When** the operator switches it to run without approval, **Then** the console asks for confirmation, naming the agent and saying that every message to it will be sent without a person seeing it first, from the next run, and that a proposal already waiting for a decision can then only be approved; nothing changes unless they confirm.
3. **Given** the switch was confirmed, **When** the next run hands work to the agent, **Then** nothing pauses for it, on the orchestrator, on its subagent, and in a background run, and the service was not restarted.
4. **Given** a run is in progress, **When** an agent is switched to run without approval, **Then** that run keeps pausing for it until it ends.
5. **Given** a saved agent that runs without approval, **When** the operator switches it to require approval and confirms, **Then** every message to it pauses for a decision from the next run on every instance.
6. **Given** a run in progress that started while an agent ran without approval, **When** the agent is switched to require approval and the run then makes a hand-off to it, **Then** nothing is sent, the hand-off gives an error result saying the agent now requires approval, and the run continues.
7. **Given** a run paused on a proposal, **When** an agent's approval choice changes and the proposal is then decided, **Then** the decision is applied under the choice in force when it arrives, by the rules that apply today after a restart with a changed configuration.
8. **Given** a paused step that also holds a hand-off to an agent that ran without approval and now requires it, **When** the proposal is decided, **Then** the resume is refused with a reason that names the agent and says why, nothing from the step runs, and the proposal stays in place.
9. **Given** a saved agent that is not answering, **When** the operator changes only its approval choice, **Then** the change is saved and the agent is not contacted.
10. **Given** an agent whose card describes it as harmless or read-only, **When** its approval choice is requiring approval, **Then** every message to it still pauses: the card decides nothing.
11. **Given** an environment agent, **When** the operator looks for a way to change its approval choice, **Then** there is none, and a request to do so sent straight to the service is refused.
12. **Given** an approval choice was just changed, **When** the catalog is read, **Then** the agent's tools carry the classification the new choice implies.

### User Story 5 - Move or remove an agent (Priority: P5)

An agent moves to another port, or is no longer wanted. The operator changes a saved agent's address: the service reads the card at the new address first and refuses the change if the agent there cannot be used, leaving the old address in place. They remove an agent they no longer need. Both ask for confirmation, and when the agent still has tasks pending the confirmation says how many: those tasks are given up, as happens today when an agent is removed from the configuration, and each thread is told.

**Why this priority**: Saved agents need upkeep. Without this the only correction is to add the agent again under another name, which leaves the old one in the orchestrator's tools, so it comes before the story that adds no capability of its own.

**Independent Test**: Add the stand-in agent and start a task on it that stays pending. Open the removal: the confirmation says one task is pending. Confirm: the card is gone, the thread state lists the task as given up, a background run tells the thread, and the stand-in received no cancel. Add the agent again, change its address to a port where nothing listens: refused, and hand-offs still reach the first address. Change it to a second stand-in: the next run's hand-off reaches the second one.

**Acceptance Scenarios**:

1. **Given** a saved agent with no task pending, **When** the operator changes its address to one where an agent can be used and confirms, **Then** the card shows the new address and the card details read there, and the next run's hand-offs go to the new address.
2. **Given** a saved agent, **When** the operator changes its address to one where no agent can be used, **Then** the change is refused with the reason, and the earlier address stays saved and in use.
3. **Given** a saved agent with three tasks pending, **When** the operator changes its address, **Then** the confirmation says that three pending tasks will be given up; once confirmed, each is listed in its thread as given up, each thread is told by a background run that the agent was moved and may still be working on the task where it was, no cancel is sent, and nothing about those tasks is ever sent to the new address.
4. **Given** a saved agent, **When** the operator removes it, **Then** the console asks for confirmation naming the agent and saying how many of its tasks are pending; once confirmed, the card is gone, the next run has neither of its tools, the catalog no longer lists it, and it is still gone after a restart.
5. **Given** a saved agent with tasks pending, **When** it is removed, **Then** each task is given up and reported in its thread as a task whose agent is no longer configured, as today.
6. **Given** a run is in progress, **When** an agent it started with is moved, **Then** that run finishes with the agent at the address it had when the run started, and the next run has the new address.
7. **Given** a run in progress that started while an agent ran without approval, **When** the agent is removed and the run then makes a hand-off to it, **Then** nothing is sent, the hand-off gives an error result saying the agent was removed, and the run continues; the next run has neither of its tools.
8. **Given** a run paused on a proposal for an agent, **When** the agent is removed and the proposal is then decided, **Then** nothing is sent whatever the decision, as today, also when an agent was added again under the same name in between.
9. **Given** a run paused on a proposal for an agent, **When** the agent is moved and the proposal is then approved, **Then** the message is sent to the agent's current address.
10. **Given** a task that was given up because its agent was moved, or was removed and added again, **When** a run tries to answer it or cancel it, **Then** nothing is sent and the call gives an error result saying the task was given up.
11. **Given** a saved agent, **When** the operator looks for a way to change its name, **Then** there is none, and a request to do so sent straight to the service is refused.
12. **Given** an agent another operator has just removed, **When** the operator changes, removes, or checks it from a page that still shows it, **Then** the request is refused as not found and the list is read again.
13. **Given** two operators have the same agent open, **When** one saves a change and the other then saves or removes from a page that still shows the earlier values, **Then** the second request is refused, nothing changes, and their page shows the agent as it is now.
14. **Given** an environment agent, **When** the operator looks for a way to move or remove it, **Then** there is none, and a request to do so sent straight to the service is refused.
15. **Given** a removed agent, **When** a thread that worked with it is read, **Then** its earlier tasks are still listed there with their final status.
16. **Given** a run in progress that started before an agent was moved, **When** another agent is saved at the address it left and the run then makes a hand-off to the first, **Then** nothing is sent, the hand-off gives an error result saying the address the run started with is another agent's now, and the run continues.

### User Story 6 - An agent's address stays inside the Agents section (Priority: P6)

The operator sees the address they entered on the agent's card, so they can check it and change it. Nobody and nothing else is given it: not the orchestrator, not a thread, not a log line, not the catalog. A page from another origin can neither read the list of agents nor change one, and cannot put the console inside itself to borrow the operator's clicks.

**Why this priority**: The rule protects every other story, and each of them is written to respect it. It is listed last because it adds no capability of its own; it is still required before anything that shows an address is released.

**Independent Test**: Add an agent on a port number chosen to be recognizable. Drive every route of the Agents section with it, refusals included, with runs that complete, pause, and fail, a check, a change of address, and a removal. Search every response outside the Agents section, every stream, every thread, the catalog, and everything the service's process logged at any level for the port: it appears nowhere. From a page of another origin, try to read the list, to add, change, remove, and check an agent, and to show the console in a frame: no response can be read, nothing changes, and the console is not shown.

**Acceptance Scenarios**:

1. **Given** a saved agent, **When** the Agents section lists it or answers an add or a change of it, **Then** the answer carries the address in the form the service keeps it in.
2. **Given** a saved agent, **When** anything else about it is returned, streamed, logged, or kept, including the catalog, a tool's description, a pause, an error result, and a refusal's reason, **Then** it names the agent and holds no address.
3. **Given** an agent saved under `localhost` or under a loopback IP address, **When** an error names the same port with this machine written another way, **Then** that form is removed too.
4. **Given** an agent whose card mentions its own address, **When** its card details are shown in the console, listed in the catalog, or used to describe its tools, **Then** the address has been removed from them.
5. **Given** a page served from another origin, **When** it asks for the agents or tries to add, change, remove, or check one, **Then** it can read no response and nothing changes.
6. **Given** a page served from another origin, **When** it tries to show the console inside itself, **Then** the browser does not show it.
7. **Given** a request to a route of the Agents section that takes a body, **When** the body is not sent as JSON, **Then** it is refused.
8. **Given** an environment agent, **When** anything about it is returned, the Agents section included, **Then** it holds no address.

### Edge Cases

- **An agent's approval is tightened while a run is in progress.** The run was started when the agent ran without approval. After the switch, a hand-off that run makes to the agent is not sent: it gives an error result saying the agent now requires approval, and the run continues (FR-022). A message whose sending had begun before the switch was answered is not recalled.
- **An agent is removed while a run in progress is talking to it.** The run keeps the agent's two tools until it ends, but nothing more is sent: a message to an agent that ran without approval gives an error result saying the agent was removed (FR-022), and one that requires approval pauses the run, whose continuation no longer has the agent. A message whose sending had begun before the removal was answered is not recalled; a task it starts is given up like the ones that were pending.
- **An agent is moved while a run in progress is talking to it.** The run finishes with the agent at its earlier address. A task such a run starts there after the change is given up like the ones that were pending when the change was made. When another agent is saved at the address it left, the run sends nothing more there: the address is that agent's now, whatever its approval choice (FR-022).
- **A step holds a hand-off that ran without approval when the run paused, and the agent now requires it.** The resume is refused, nothing from the step runs, and the proposal stays in place, as features 002 and 003 already decide after a restart. Until now this needed a restart; an operator can now cause it from the console, so the refusal names the agent and the reason (FR-023), and the confirmation for requiring approval warns of it. The thread can continue once the agent runs without approval again or is removed.
- **An agent is switched to run without approval while proposals for it wait for a decision.** Each such proposal then accepts approve only, as today after a restart: it is sent as proposed once approved, and can no longer be rejected or edited. The confirmation says so (FR-011).
- **A proposal is waiting for a decision when its agent is moved, or removed and added again under the same name.** A proposal names its agent and never an address. A moved agent is the same agent: an approval sends the message to its current address, and the confirmation for the move says so. An agent removed and added again is a different agent: the earlier proposal is decided as the tool under that name now allows, and nothing is sent whatever the decision: the call gives an error result saying that the agent it was proposed for was removed (FR-023).
- **An agent is removed and later added again under the same name.** It is a different saved agent: a request from a page that still showed the earlier one is refused (FR-012). Threads continue the conversation they had under that name, as they do today when an agent leaves the configuration and comes back; what the agent at the new address remembers of it is the agent's responsibility. Tasks given up at the removal stay given up, and nothing about them is sent to the new agent (FR-025); a proposal that was waiting for the earlier agent is never sent (FR-023).
- **The environment gains an agent or a tool server with a saved agent's name, a tool with the name of one of its tools, or an agent at its address.** After the restart that applies it, the environment's entry is the one in use. The service starts, the saved agent is listed as not in use with the reason, its pending tasks are given up as at a removal, a proposal that was waiting for it is never sent to the environment's agent, and the only thing the operator can do with it is remove it. Removing it leaves the environment agent's own tasks alone. The other way round is the same: when an agent leaves the environment and a saved agent is later given its name, the tasks and proposals of the first never reach the second (FR-023, FR-025).
- **The card an agent serves changes after it was added.** The card is read again whenever the service connects to the agent. If it can no longer be used, for example because it now requires authentication, the agent is listed as unreachable with that reason and hand-offs to it fail until it can be used again; it stays saved. If it can be used but says something else of itself, what the console shows and what the orchestrator is told stay as they were until the operator checks the agent (FR-015).
- **An agent's card is very large, or lists hundreds of skills.** A card document larger than one megabyte cannot be used. Of a smaller one, the service keeps and shows the first 2,000 characters of each text, the first 50 skills, and the first 50 tags of a skill, and the card in the console says that it was cut (FR-002).
- **An agent's card claims a different name than the operator gave.** The operator's name is the one Freyja uses everywhere; the card's name is shown as the agent's own claim.
- **Two agents at one address.** Refused: an address that is already another agent's, saved or from the environment, cannot be saved (FR-006). Two names for one destination with different approval choices would let the choice of tool decide whether a message pauses.
- **The address points at something that is not an agent**, such as the service itself or the web app. No usable card is read there, so it is refused like any address where none can be read.
- **The address is one where the card is served only after a redirect.** No redirect is followed, as today, so the card cannot be read and the agent is refused.
- **The same address is entered in another spelling**, with capitals, a trailing slash, or the port left out. The service keeps one form (FR-006), shows that form, and compares that form: an entry that comes to the saved form is not a change of address.
- **A check is asked for an agent that is being checked, or a fifth card read is asked while four are under way on that instance.** It is refused and contacts nothing. A change or a removal of an agent that is being checked goes ahead; the check finishes with the address it started with, its result is reported to whoever started it with a note that it was not recorded, and it is not recorded for an agent that has since moved or gone.
- **The console gets no answer to a request that changes something**, for example because the request took longer than the web app's server waits. The change may or may not have been made. The console says that the outcome is not known, never that it failed, and reads the list again.
- **The service stops in the middle of a change.** After the restart the change either was made in full, with its tasks given up, or was not made at all.
- **Two operators add an agent at the same moment, on two instances.** The limits and the rules on names and addresses hold: at most one of two adds that conflict is saved.
- **The operator's page is stale when a confirmation is open.** The confirmation shows the agent, and its number of pending tasks, as the list has them at that moment. A change or removal asked from values that are no longer current is refused (FR-012). A task that becomes pending between the confirmation and the change is given up too; the console then says how many were given up.
- **More saved agents than the limit are requested.** Adding one more is refused with the limit named.
- **An instance cannot read the current set of agents when a run starts.** The run does not start on an earlier set: it ends with an error, as a run does today when the active LLM profile cannot be read.
- **Several instances share a database but not a machine.** An address on this machine means that instance's machine. The service does not detect it: each instance reaches whatever answers at the address where it runs, and the reachability a card shows is that of the instance that answered.
- **Several instances are given different environment agents or tool servers.** Each instance decides from its own environment whether a saved agent is in use. An instance whose environment overrides a saved agent lists it as not in use and gives up its pending tasks, for every instance, while another instance still hands work to it. The service does not detect this.
- **No agent is configured at all, then the first one is added.** The next run has everything a run with agents has today, including the list of the thread's pending tasks and the tool that checks them. When the last agent is removed, threads keep listing the tasks they started.
- **A task is given up while no usable LLM profile is active.** It is listed as given up at once; the thread is told once a usable profile is active, since no background run starts before (feature 004, FR-016a).
- **The Agents section is opened in a narrow window.** Every control stays reachable, as in the LLM section.

## Requirements *(mandatory)*

### Functional Requirements

**The Agents section**

- **FR-001**: The Agents section MUST show every configured agent as a card with: its name; its approval choice; whether it comes from the environment; its state, one of four: reachable, unreachable, not tried yet by the answering instance, or not in use (FR-017); when the most recent attempt to use it was; the reason when it is unreachable or not in use; and the name, description, version, and skills from its card. A saved agent's card MUST also show its address. The section MUST have an Add button and MUST say that no agent is configured when none is.
- **FR-001a**: The console MUST warn about every agent that is unreachable or not in use, whether it was found so at startup or later, in three places: on the agent's own card, marked as a warning with the reason and the time; above the cards of the Agents section, in a warning that names each such agent; and on the Agents entry of the sidebar, in every section of the console, with the number of such agents. A warning MUST say what it is about in words and MUST NOT rest on color alone. The warnings show the list as the console last read it: the console reads the list when it is opened on any section and whenever the Agents section reads it, and a warning about an agent goes once a reading finds the agent reachable. With every agent reachable there is no warning, an agent the answering instance has not tried yet is not warned about, and when the service cannot be reached no warning about an agent is shown as if it were current.
- **FR-002**: What an agent's card says MUST be presented as the agent's own claim, apart from the approval choice, and MUST be shown as plain text, as MUST every reason: nothing in it is rendered as markup, loaded, or followed as a link. The service MUST cut each text of a card to its first 2,000 characters, its skills to the first 50, and the tags of a skill to the first 50, before it keeps or returns them, and the card in the console MUST say when it was cut.
- **FR-003**: The reachability a card shows is the outcome of the most recent attempt by the answering service instance to use the agent: reading its card, a hand-off, an answer, a cancel, or watching a task. Reading the list, and reading the catalog, MUST contact no agent.
- **FR-004**: The web app MUST read and change agents only through the service's API, on the origin it is served from, as the LLM section does (feature 004, FR-003). It MUST call no agent itself and decide nothing about approval itself. When the service cannot be reached or refuses a request, the page MUST say so with the service's reason, offer to try again, and never present earlier data as current. When a request that changes something gets no answer, the page MUST say that the outcome is not known and MUST read the list again. When the service cannot read its saved agents, the list, which returns addresses and the versions a change is made from, MUST answer with an error and never with an earlier list (the catalog and a thread's state are in FR-019). A form MUST keep nothing once it was sent successfully or closed.

**Saved agents**

- **FR-005**: The service MUST keep saved agents. A saved agent has a name, an address, and an approval choice, which is requiring approval unless the operator chose otherwise. Saved agents MUST be kept in the service's database, MUST survive a restart, and MUST be the same for every service instance sharing the database.
- **FR-006**: A name MUST be in the form environment agents already use: lowercase letters, digits, hyphens, and underscores, starting with a letter, at most 32 characters. It MUST differ from every other agent's name, saved or from the environment, and from every tool server's name, and neither of the agent's two tool names MAY be the name of another tool. An address MUST be a web address of at most 2,000 characters whose host is this machine, under the rule environment agents already follow: `localhost` or a loopback IP address. It MUST NOT carry a user name, a password, a query, or a fragment. The service MUST keep and show an address in one form: scheme and host in lowercase, the port always written, and no trailing slash. An address MUST NOT lead where another agent's does, saved or from the environment: the same port and path, however this machine is written. An approval choice MUST be exactly one of the two. At most 20 agents MAY be saved. A request that breaks any of these MUST be refused, name the value and the rule, and save nothing; the refusal MUST NOT repeat the address. These rules MUST hold when two requests arrive at the same moment, on one instance or on two.
- **FR-007**: An agent can be used when its card can be read at its address within the time limit, without following a redirect, the card document is no larger than one megabyte, and the card does not require authentication, accepts text or names no kind of input at all, and offers an interface Freyja speaks. Apart from the size, these are the checks the service makes of an environment agent today.
- **FR-008**: An operator MUST be able to add an agent from the Agents section. Adding MUST read the agent's card first. An agent that cannot be used (FR-007) MUST be refused with the reason, and nothing is saved.
- **FR-009**: An operator MUST be able to change a saved agent's address and its approval choice. A change of address MUST read the card at the new address first and MUST be refused, with the reason and with the earlier address left in place, when the agent there cannot be used. A change of the approval choice alone MUST NOT contact the agent and MUST NOT be refused because of the agent's state. A saved agent's name MUST NOT be changeable, from the console or by a request sent straight to the service.
- **FR-010**: An operator MUST be able to remove a saved agent. A removed agent MUST stay removed after a restart.
- **FR-011**: The console MUST ask for confirmation before: adding an agent that runs without approval; any change of a saved agent's approval choice; any change of its address; and any removal. No request that changes anything is sent before the operator confirms, and confirming MUST take an action of its own: pressing Enter in a field of the form, or the second press of a double press, does not confirm. A confirmation MUST name the agent, show it as the list has it at that moment, and say what the change means:
  - for running without approval: that every message to the agent will be sent without a person seeing it first, from the next run, and that a proposal for the agent already waiting for a decision can then only be approved;
  - for requiring approval: that it holds at once, also for runs in progress, and that a paused step holding a message to this agent that needed no approval cannot be continued until the choice is changed back or the agent is removed;
  - for a change of address: that it applies from the next run, that a run in progress finishes at the earlier address, that a proposal for the agent already waiting for a decision will go to the new address once approved, how many of the agent's tasks are pending, and that they will be given up;
  - for a removal: that it holds at once, also for runs in progress, how many of the agent's tasks are pending, and that they will be given up.
- **FR-012**: A change or a removal MUST be refused, with nothing changed, when the saved agent was changed, or removed and added again, since the page that asks last read it; the console MUST then read the list again and show the agent as it is. An agent removed and added again under the same name is a different saved agent.
- **FR-013**: An operator MUST be able to check any agent that is in use, saved or from the environment. A check reads the agent's card again and reports whether the agent can be used (FR-007), with the reason when it cannot. It updates the agent's reachability and, when the card can be used, the card details kept for it (FR-015). Its answer MUST say whether details that were kept or shown before were replaced by different ones, and the console MUST say so, with the fact that the agent's tools are described from the new details from the next run. It MUST change nothing else: not the agent's address or approval choice, not a thread, and not a pending task.
- **FR-014**: The card read made for an add, a change of address, or a check MUST end within the service's time limit for reading a card, and within twenty seconds whatever that limit is set to. On each service instance an agent MUST have at most one check in progress, and at most four such card reads MAY be under way at once. A request beyond either limit MUST be refused, say why, and contact no agent. The result of a check MUST NOT be recorded for an agent that was moved or removed while the check ran, and its answer MUST say that it was not recorded.
- **FR-015**: The card details of a saved agent MUST be kept with it, in the cut form of FR-002, so that they are shown, and its tools are described from them, whether or not the agent can be reached and on every instance alike. They are set when the agent is added and replaced only when the operator moves it or checks it and the card read can be used. A card the service reads by itself decides whether the agent can be used and changes nothing the console shows or the orchestrator is told of the agent. An environment agent's card details are those the answering instance last read, as today.
- **FR-016**: The reason given when an add, a change of address, or a check finds that an agent cannot be used MUST be one of a fixed set of sentences the service words itself, one per way of failing: nothing answered at the address, no answer in time, no card there, a card that cannot be read, a redirect, a card that is too large, a card that requires authentication, a card that accepts no text, and a card that offers no interface Freyja speaks. Text supplied by the agent or by a library MUST NOT be passed on in it.

**Environment agents**

- **FR-017**: Every agent named in `FREYJA_A2A_AGENTS` MUST appear in the Agents section marked as coming from the environment, with the approval choice the environment gives it. It MUST NOT be changeable or removable, from the console or by a request sent straight to the service, and its address MUST NOT be shown, in the Agents section or anywhere else. A saved agent MUST NOT take an environment agent's name or address (FR-006). When the environment later gains an agent or a tool server with a saved agent's name, a tool with the name of one of its tools, or an agent at its address, the environment's is the one in use: the service MUST start, MUST list the saved agent as not in use with the reason, MUST give up its pending tasks as at a removal, MUST never send a proposal that was waiting for it to the environment's agent (FR-023), and MUST let the operator remove it and do nothing else with it. When a later restart takes away what overrode it, the saved agent is in use again as it was saved: the tasks given up meanwhile stay given up, and a proposal still waiting for it is decided as for any saved agent in use.
- **FR-018**: An environment entry that is invalid in itself MUST stop startup with an error naming the agent, as today: a name not in the allowed form, a missing address, an address that is not on this machine, a setting the configuration does not define, a name shared with a tool server, or a tool name already taken. Those are invalid settings, which FR-020 does not cover.

**Taking effect**

- **FR-019**: Adding, changing, or removing an agent MUST take effect without a restart. A run that starts on any service instance after the change was answered MUST have the new set of agents, with each agent's current address and approval choice, on the orchestrator and on its subagent: the set is the one in force when the run starts, on every instance. A run in progress MUST keep the tools it started with, including a removed agent's, and an earlier address of an agent that was moved; what it does not keep is leave to send what FR-022 keeps back: nothing reaches an agent that was removed, nothing unseen reaches one that now requires approval, and nothing reaches an earlier address that has become another agent's. A paused run that is continued afterwards, and a background run that starts afterwards, have the new set. A run that cannot learn the current set when it starts MUST NOT start on an earlier one and ends with an error. Starting a run MUST NOT wait for an agent. On an instance other than the one that handled the change, the list and the catalog MUST follow at their next reading, and the watching of pending tasks at its next round, which comes within ten seconds at the default settings; the catalog lists the agents and tools the answering instance's next run would have. While an instance cannot read the saved agents, its catalog and its thread states answer from the set it last had.
- **FR-020**: The service MUST start when an agent, saved or from the environment, cannot be used (FR-007). It MUST log a warning that names the agent and the reason, and MUST list the agent as unreachable with the reason and the time; every other agent and every other part of the service MUST work. The health check MUST keep reporting only that the service runs.
- **FR-021**: Which agents the orchestrator has tools for, and whether each is gated, MUST depend on the configuration alone, never on whether an agent answers. An agent that cannot be used keeps its two tools. A hand-off, an answer, or a cancel to it MUST become an error result naming the agent, the run MUST continue, and nothing is retried, as today for an agent that stops answering. Nothing MAY be sent to an agent from which the instance has read no usable card at its current address. An agent that was down and answers again MUST be usable without a restart and without any action by the operator: a hand-off to an agent the instance has no usable card from reads the card first, inside the hand-off's own time limit. An environment agent whose card the instance has not read has its tools described by its name alone until it is.

**Approval**

- **FR-022** (amended by feature 010: the agents' approval mode decides with the choice): An agent's approval choice MUST be the only thing that decides whether a message to it pauses for a decision: a hand-off, a follow-up, an answer, and a cancel alike, on the orchestrator, on its subagent, in the continuation of a resumed run, and in a background run. The rule is the one feature 003 set (its FR-011 and FR-012), with the saved choice in place of the environment's for a saved agent. What the agent's card says, whether the agent can be reached, and the model's own judgment MUST NOT influence it. No code path MAY send a message to an agent that requires approval without an approve or edit decision for that proposal. To that end, before any message to a saved agent is sent, whether or not a person decided it, the service MUST find that the saved agent the run started with still exists at that moment; before one that no person decided, also that the agent still runs without approval; and, when the run still has the agent at an earlier address (FR-019), that the address has not become another agent's. When the agent was removed, also when another agent was since added under its name, when it now requires approval, or when its earlier address is another agent's now, nothing is sent, the call gives an error result saying which of the three it was, and the run continues. A switch to requiring approval and a removal therefore hold at once, on every instance and for runs in progress; a switch to running without approval holds from the next run. A message whose sending began before the change was answered is not recalled.
- **FR-023**: A decision on a pending proposal MUST be applied under the agents and approval choices in force when the decision arrives, by the rules features 002 and 003 already apply after a restart with a changed configuration: a message to an agent that was removed is never sent, whatever the decision; a message to an agent that now runs without approval accepts approve only; and when a call in the paused step has come to require approval since the pause, the resume is refused, nothing from the step runs, and the proposal stays in place. That last refusal MUST name the agent and say that it now requires approval. A proposal names its agent and never an address, and belongs to the saved agent it was proposed for. After that agent was moved, an approval sends the message to its current address. After it was removed, also when another agent was since added under its name, the message is never sent, whatever the decision. A proposal for an environment agent follows the agent's name across a restart, as today, for as long as the name is an environment agent's. A proposal never passes between an environment agent and a saved agent that come to hold one name: one made for a saved agent the environment now overrides (FR-017), and one made for an environment agent whose name a saved agent was given after it left the configuration, is never sent, whatever the decision.

**Pending tasks**

- **FR-024**: Removing a saved agent, or changing its address, MUST give up every task of that agent that is pending when the change is applied, in the way a task is given up today when its agent leaves the configuration: the task is listed in its thread as given up, a background run tells the thread that Freyja stopped waiting and that the agent may still be working, and no cancel is sent. For a moved agent the report says that the agent was moved and offers no cancel. A task that ended before the change was applied keeps its outcome. The change and the giving up MUST happen together or not at all. The list MUST report each saved agent's number of pending tasks, the service MUST tell the console how many tasks a change gave up, and the console MUST say so.
- **FR-025**: A task belongs to the saved agent as it was when the task started. Once that agent was moved, or removed, also when an agent is later added under the same name, the task MUST never be checked, answered, or canceled at the agent's later address: an answer or a cancel for it gives an error result before anything is sent. A task that a run in progress starts at the earlier address after the change is given up as well. Nothing an agent at an earlier address gave the service, such as a cookie, MAY be sent to a later one. Tasks of an environment agent follow its name, as today, for as long as the name is an environment agent's. A task never passes between an environment agent and a saved agent that come to hold one name: it is given up, and an answer or a cancel for it gives an error result before anything is sent.
- **FR-026**: A change of the approval choice alone, and a check, MUST leave pending tasks as they are. Tasks of an agent that cannot be reached stay pending and are watched as today, and the service MUST keep trying to reach such an agent while it has a task pending, at most once in each round of watching, so that the tasks are checked again once it answers. A removed agent's earlier tasks MUST stay listed in their threads, and a thread's conversation with an agent MUST stay tied to the agent's name.

**The address, and other origins**

- **FR-027**: By itself the service MUST contact an agent only to read: its card, and the status of a pending task. It MUST send an agent a message, an answer, or a cancel only in a run, under the approval rules (FR-022). Adding, changing, and checking an agent read its card and nothing more. Every request to an agent MUST go to the host and port of its address, directly: never to an address taken from its card or from a redirect, as today, and never through a proxy the environment configures.
- **FR-028**: A saved agent's address MUST be returned only by the Agents section's own routes, in the list and in the answer to an add or a change, and only in the body of an answer; an address is sent to the service only in the body of a request. It MUST NOT appear in the catalog, a tool's name or description, a pause, an error result, a log line, or the reason of a refusal or a failed check. Text about an agent that the service words itself or takes from a library's error, and an agent's card details, MUST have the address removed in each of these forms: as kept; its host and port; and its port after `localhost`, `127.0.0.1`, and `[::1]`. No line the service's process logs, at any level and from any library it uses, may hold the address. For environment agents this extends what feature 003 removes today, which is the address as configured. An address that was sent to the service and refused is kept out of the same places: its refusal does not repeat it (FR-006), and no line logged while it was tried holds it. What an agent writes in its own replies and progress updates passes through as today and is not searched.
- **FR-029**: The routes of the Agents section MUST NOT be usable by a page served from another origin: such a page can neither read a response nor add, change, remove, or check an agent, including through the routes that take no body. A request to a route that takes a body MUST be refused when the body is not sent as JSON. The rule and its refusal are the ones the LLM routes already apply (feature 004, FR-003a). The console MUST NOT be displayable inside a page of another origin.
- **FR-030**: The service MUST log, naming the agent and never its address, each agent added, changed, with which of its values changed, removed, with how many tasks were given up, and checked, with the result and whether its card details were replaced. It MUST log each message that an agent's tool kept back under one of the fixed rules of FR-021 to FR-025, with the agent's name and which rule it was, and each resume refused because a call came to require approval (FR-023). A proposal whose agent no longer has a tool is handled as today. At startup it MUST log as a warning each agent that cannot be used or is not in use, with the reason. Afterwards it MUST log the same warning when it finds either out: that an agent is not in use, when it learns of a change, and that an agent cannot be used, when a card read for it fails.

**Compatibility and quality**

- **FR-031**: With no saved agent and every environment agent answering at startup, every behavior of the service MUST be what it was before this feature, and every existing automated test MUST pass unchanged, apart from: the tests that expect startup to fail for an agent whose card cannot be read or cannot be used, which now start the service (FR-020); the one test that expects an unnamed error when a resume is refused because a call came to require approval, which now names the agent (FR-023); and the two tests of the Agents placeholder page, which is replaced. A test file MAY gain setup, or names it collects, without any of its checks changing: every page of the console now asks for the list of agents, so the sidebar's unit tests and feature 004's end-to-end tests are handed an answer for it. With no agent configured at all, saved or from the environment, the orchestrator's tools and the catalog MUST be what they are today with none configured.
- **FR-032**: The service's behavior and the web app's behavior MUST each be covered by automated tests that need no network and no agent installed or running, with the stand-in agent in the agent's place. The console's part of every user story MUST also be covered by an end-to-end test that drives the console in a browser, beside its unit tests. The tests MUST include a search for a recognizable address in everything the service returns outside the Agents section, streams, keeps, and logs at any level.

### Key Entities

- **Delegate agent**: An agent the orchestrator may hand work to. It has a name, an address on this machine, an approval choice, where it comes from (saved by an operator, or the environment), its card details, and the outcome of the most recent attempt to use it. Its name is fixed for its whole life: its two tools and every conversation held with it are named after it.
- **Saved agent**: A delegate agent an operator added through the console. It belongs to the service's database and is the same for every instance, its card details included. Its address is shown back in the Agents section and nowhere else. One removed and added again under the same name is another saved agent.
- **Environment agent**: A delegate agent named in `FREYJA_A2A_AGENTS`. It is read from the service's configuration, never stored, and cannot be changed from the console. With several instances, it is what the answering instance was given.
- **Approval choice**: Whether messages to an agent require a person's approval or run without it. Requiring approval is the default. It is the operator's decision and the only input to the gate for that agent.
- **Agent card**: What an agent publishes about itself: its name, description, version, skills, and what it accepts. It decides whether the agent can be used at all and describes its tools; it never influences approval. Its text is untrusted.
- **Reachability**: Whether the most recent attempt to use an agent succeeded, when, and why not. It belongs to one service instance and is not stored; it starts again when the instance starts.
- **Check**: One reading of an agent's card at an operator's request, with whether the agent can be used and the reason when not.
- **Pending task**: As in feature 003. New here: it belongs to the saved agent as it was when the task started, and is given up when that agent is removed or moved.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator who has a running agent's address at hand can add it and have the next run hand work to it in under two minutes, without editing a file and without restarting anything.
- **SC-002**: After an agent is added, changed, or removed, 100% of the runs that start afterwards, on any instance, have the new set.
- **SC-003**: No run in progress fails or stops because an agent was added, changed, or removed while it ran. What changes for it is that a message FR-022 keeps back is not sent: one to an agent that was removed, one nobody decided to an agent that has come to require approval, and one to an earlier address that has become another agent's.
- **SC-004**: In the automated suite, 100% of messages to an agent that requires approval pause for a decision, whether the agent is saved or from the environment, whether proposed by the orchestrator, its subagent, or a background run, and whether a hand-off, a follow-up, an answer, or a cancel. By the stand-in agent's own record, zero messages reach it without an approve or edit decision after a switch to requiring approval was answered, and zero messages of any kind after its removal was answered, from runs in progress included. A message whose sending had begun when the change was answered is not counted (FR-022).
- **SC-005**: In 100% of automated runs, an operator switching an agent to run without approval is told before they confirm that nothing sent to it will be seen by a person first, and an agent added without touching the approval choice requires approval.
- **SC-006**: The service starts and serves requests whatever number of its agents are down or unusable, in 100% of automated runs, and no later than the time limit for reading a card after it would with every agent answering.
- **SC-007**: An agent that is refused when added or moved leaves nothing behind: the list, the catalog, and the next run's tools are what they were, in 100% of automated runs.
- **SC-008**: A recognizable address of a saved agent appears in none of the forms FR-028 lists in anything the service returns outside the Agents section, streams, keeps in a thread, or logs at any level, through every route of the Agents section and through runs that complete, pause, and fail.
- **SC-009**: A page served from another origin can read no agent and add, change, remove, or check none: the service gives permission to no other origin on any route of the Agents section, refuses each of its changing routes to a request a browser marks as coming from another origin, and the console cannot be shown inside another origin's page.
- **SC-010**: Every task pending for an agent when it is removed or moved is listed as given up at once and reported in its thread exactly once, within one minute at the default settings while the thread is free and a usable model is active. The agent at the new address receives zero checks, answers, and cancels for such a task.
- **SC-011**: Adding, changing, and checking an agent send it zero messages and zero tasks, by the stand-in agent's own record, in 100% of automated runs.
- **SC-012**: An add, a change of address, and a check each end within twenty seconds, whatever the agent does and whatever the time limit is set to.
- **SC-013**: In 100% of automated runs, saved agents are the same after a restart as before it: names, addresses, approval choices, and card details.
- **SC-014**: A deployment configured only through the environment, with every agent answering, behaves exactly as before: every automated test that existed before this feature passes, changed only as FR-031 lists.
- **SC-015**: With twenty saved agents, the Agents section shows its cards within two seconds on the machine the service runs on.
- **SC-016**: A change or removal asked from a page that shows an agent as it no longer is changes nothing, in 100% of automated runs.
- **SC-017**: While an agent is unreachable or not in use, an operator who opens the console on any section sees a warning without opening the Agents section, and in the Agents section sees which agent it is and why, in 100% of automated runs; with every agent reachable the console shows no such warning.

## Assumptions

**Scope**

- Out of scope, per the description: tool servers reached over MCP, which stay configured through the environment; agents on another machine; agents that need credentials; authentication for the console or the API; a different set of agents per thread; and renaming a saved agent.
- Also out of scope: changing or removing an environment agent from the console; importing the environment's agents into the database; turning an agent off without removing it; reordering or grouping cards; a history of checks; showing an agent's tasks or conversations in the console, which stay in the thread state; the time limits and the task settings of feature 003, which stay in the environment and apply to saved agents as they do to environment agents; stopping a run in progress from the console; and sending an agent a test message, which would be work handed to it without a run and without the gate.
- Left open by feature 004 on purpose and not addressed here: a request that reaches the service under a name an attacker controls (DNS rebinding), which the refusal of other origins does not cover. With this feature that gap also covers the routes that change an approval choice. Also not addressed: what a deployment records about an agent by means other than responses, streams, threads, and log lines, such as tracing it turns on. FR-028 and SC-008 cover those four, and nothing here configures or cleans a trace.
- The console is in English and is used with a current desktop browser, as in feature 004.

**Behavior choices**

- An environment agent that cannot be used no longer stops startup (FR-020). The description says an agent that cannot be reached when the service starts does not stop it, and also that environment agents keep working unchanged; the constitution's principle IV says a deployment configured only through the environment behaves as it did before. The first is taken to hold for every agent and for every problem with a card, not only an agent that does not answer: one rule for both kinds, and a deployment whose agent is briefly down can still start and open its console. A deployment whose agents answer behaves as before, which is how feature 004 read the same sentence of the constitution when it let the service start without a usable model. This is the largest change to existing behavior in this feature. Confirmed in clarification on 2026-11-19, with the warnings FR-020 and FR-001a now ask for, in the log and in the console; keeping today's stop for environment agents, and starting only when an agent does not answer, were considered and not adopted.
- A switch to requiring approval and a removal hold at once, for runs in progress too (FR-022). The description says runs in progress finish with the agents they started with. For a run's tools and for the address of an agent that was moved, that is what this specification says. For the leave to send without approval it is not: the constitution's principle I allows no path past the gate, and an agent an operator has just put under approval or removed would otherwise keep receiving unseen messages until every run in progress ended. Confirmed in clarification on 2026-11-19; cutting off only a tightened agent, and keeping both as the run started, were considered and not adopted.
- A change of the approval choice alone does not read the agent's card (FR-009). The description says changing an agent reads its card first and refuses when it cannot be read. Read literally, an operator could not put an agent back under approval while it is down, which is when they may most want to. The card says nothing about approval, so the card is read when the address changes and not otherwise. Confirmed in clarification on 2026-11-19; reading it only before a switch to running without approval, and always reading it, were considered and not adopted.
- Every change of a saved agent is confirmed, not only the switch to running without approval (FR-011). Each one changes what the running service does, and the confirmation for requiring approval carries a warning of its own. Adding an agent that requires approval is not confirmed: saving the form is the deliberate act, and every message to the new agent still waits for a person.
- A change asked from stale values is refused (FR-012), where feature 004 keeps the later save. With last-save-wins, a page that still shows an agent as running without approval could put it back there while its operator confirmed only a change of address.
- A task belongs to the address it was started at (FR-025), so after a move it can be neither answered nor canceled through Freyja, and the report offers no cancel. The description gives such tasks up; the rest follows from not asking one agent about a task another agent was given. An operator who needs the task stopped stops it at the agent.
- A pending proposal follows its saved agent across a move and not across a removal and a new addition (FR-023). Moving an agent is the operator vouching for the new address under the same name, which is what the approver was shown; an agent added again is another agent. Confirmed in clarification on 2026-11-19; always following the name, and never sending after either, were considered and not adopted.
- A thread's conversation follows the agent's name, across a move and across a removal and a new addition (FR-026). Feature 003 already sends a thread's conversation and leaves what the agent remembers to the agent.
- One address, one agent (FR-006). The description does not ask for it; two names for one destination with different approval choices would let the choice of tool decide whether a message pauses. Any way of writing this machine counts as the same host, so two listeners on different loopback addresses with the same port and path cannot both be saved. The rule compares what was saved. A message goes to the path the agent's card names for its interface, on the saved host and port (FR-027), so two agents saved at different paths of one port whose cards name the same interface are two names for one endpoint, and the rule does not catch that: catching it would mean trusting what a card says. Confirmed in clarification on 2026-11-19.
- What the orchestrator is told of a saved agent changes only when an operator adds, moves, or checks it (FR-015). A card is untrusted text that reaches the model. It changes only by the operator's own act, the console shows what was read, and a check says when it replaced what was kept (FR-013). The console does not ask before the text is used: it is used from the next run, so the operator sees it no earlier than the model does.
- The reason for a refused add, move, or check is the service's own sentence (FR-016), not the library's or the agent's text. It tells the operator which kind of failure it was and passes nothing back from whatever answered at the address.
- An agent that cannot be used keeps its tools (FR-021). The description says hand-offs to it fail as they do today for an agent that stops answering, which they can only do if the orchestrator can still propose them.
- Reachability belongs to each service instance and is not stored (FR-003), as it is today. Two instances can show different outcomes for one agent.
- An environment agent's address is not shown (FR-017). The description shows back the address an operator entered in the console; an environment agent's was not entered there, cannot be changed there, and may be written in a form that carries a credential.
- The console may not be shown inside another origin's page (FR-029). The description does not ask for it. Confirmations are what stand between an operator's click and a removed human check, and a page that frames the console can draw that click; the rule covers the LLM section as well. Confirmed in clarification on 2026-11-19.
- Limits chosen here: 20 saved agents, since each adds two tools to every run of the orchestrator and its subagent; 2,000 characters for an address and for each text of a card, 50 skills, and 50 tags of a skill; one megabyte for a card document; four card reads at once on an instance; and twenty seconds for a card read the console asked for, which is the service's default limit and stays below the thirty seconds the web app's server waits for an answer.
- There is no check of unsaved form values. Saving an address is itself a check, and saves nothing when it fails.
- Trust, stated in one place. The operator is trusted: the approval choice is theirs, and anyone who can reach the console can remove the human check for an agent. The model is not trusted to decide what needs approval. An agent is not trusted with effects, which is why messages to it are gated unless the operator chose otherwise, and its card is untrusted text that reaches the model, the approver, and now the console, where it is shown as plain text (FR-002). Marking an agent as running without approval means whatever the orchestrator writes to it is sent unseen; the operator accepts that for each such agent, and the confirmation says it.

**Earlier requirements this feature replaces**

- Feature 004, FR-002: the Agents section no longer says that agents are not managed from the console.
- Feature 003, FR-002 and the edge case "Configuration changes while the service runs": agents are no longer read once at startup, and a change no longer waits for a restart.
- Feature 003, FR-003, SC-005, User Story 6 scenarios 1 and 2, and the assumption that an agent not running at startup is a startup failure: a problem with an agent's card no longer stops startup (FR-020). The entry-level cases of FR-003 still do (FR-018).
- Feature 003, FR-022, for one case: a task given up because its agent was moved cannot be canceled (FR-025).
- Features 002 and 003, the resume refused because a call came to require approval: its error now names the agent (FR-023).

**Environment and dependencies**

- The constitution's principle IV already names delegate agents as operator-managed configuration, kept in the database and changed only through the API, with the environment's agents staying valid as a read-only default. No amendment is needed. Principle I is what the approval choice touches: the gate itself, its decisions, and its rules are unchanged, and the choice stays a value the operator sets, never one a model or an agent's card influences.
- The service keeps binding to the local interface with no authentication. With this feature, anyone who can reach the port can add an agent, remove one, and switch an agent's approval off, as they can already approve any proposal; that includes any process on this machine, a delegate agent among them. That is acceptable for local use, is documented, and must be revisited before the service is bound more widely. Two further exposures share that condition: anyone who can reach the port can make the service request a card from any port of this machine and learn which kind of failure it met, and can read the list of saved agents with their addresses. FR-014 limits how many card reads run at once; no limit is set on how often an agent is added, moved, or checked over time.
- Several service instances may share one database, as before. They are assumed to run where the same local addresses reach the same agents, and to be given the same environment agents and tool servers; the service does not check this (Edge Cases). They are also assumed to all run a version of the service that knows saved agents before the first agent is saved: an instance on an earlier version has none of a saved agent's tools and gives up its pending tasks, as it does today for an agent that left the configuration.
- The existing thread routes, approval gate, resume rules, run lease, step limit, catalog, hand-off and cancel tools, send ledger, conversations, pending tasks, and delegation worker are reused. This feature adds saved agents, the routes the console needs, the check, and the Agents section, and changes three things: the set of agents becomes something the running service takes up when it changes, in the way feature 004 made the model; an agent that cannot be used no longer stops startup; and every message to a saved agent is checked against the saved agent first.
- The stand-in agent of feature 003 plays every agent in the automated tests, as it does today.
