# Feature Specification: Receive Tasks from Other Agents over A2A

**Feature Branch**: `009-a2a-server`

**Created**: 2026-11-25

**Status**: Draft

**Input**: User description: "Receive tasks from other agents over A2A. Until now Freyja only hands work to other agents (features 003, 005, 006). This feature lets other agents hand work to Freyja: Freyja serves the A2A protocol itself, with an agent card that says what it is, so that an agent such as ARTEX or heimdall can send it a message, follow the task, and read its result. Off by default; with it off the service behaves exactly as before. Who may call. An agent on the service's own machine calls on the service's own address with no credential, since anything there can already start a run through the thread routes. An agent on another host calls a second listener, off by default, with its own address and port, that serves only the agent card and the A2A operations and nothing else of Freyja's API (not threads, agents, or LLM profiles), and every A2A operation there must carry a bearer token of a caller the deployment named; the card itself is readable without one. Callers and their tokens are deployment configuration from the environment; a token is never returned, logged, streamed, or written to a thread. The address the card advertises is configuration too. Freyja's own API and console stay unauthenticated and on this machine. What a message does. A message with a new conversation (context) starts a new Freyja thread, whose id Freyja chooses, and a run on it of the kind the console starts, which goes on whether or not the caller keeps reading (feature 007). Another message in the same conversation from the same caller continues the same thread, as a follow-up in the console does, and is refused while a run is in progress or a proposal is pending on it. A conversation is private to its caller: one caller can never continue or read another caller's conversation, nor a thread started from the console or the API. A message aimed at a task that has not ended is refused. Approval (constitution principle I, unchanged). A run a caller started pauses on any action that needs approval exactly as any run does. Only a person decides, in the console's Tasks section; a calling agent can never approve, edit, or reject. While it waits, the caller sees the task as still working, with a status message that says it waits for a person's approval and names the actions without their arguments. Nothing a caller sends is ever taken as a decision. What the caller sees. The task's state as it changes (working, completed, failed, canceled); a status update as each step completes that names the step (which tool or agent was used) without arguments or results; Freyja's own reply as it is written, streamed, and as the task's result when the run ends. Never a subagent's or a delegate agent's messages, never a tool's arguments or results, never a stored API key beyond what feature 004 allows, never a delegate agent's address (005), never another caller's token. A caller can read a task and subscribe to it again later, after a restart and on any instance sharing the database. Push notifications and an extended card are not offered. Cancel. A caller can cancel its own task: a run in progress is stopped between two steps as the console's Stop does (007), never cutting an action off; a task waiting for approval has its pending proposal rejected with the reason that the requesting agent canceled, so that nobody approves an action whose requester is gone. The console. A task a caller started appears in the Tasks section like any other, marked with the caller that started it. A person decides its proposals and can stop it there, and cannot send a follow-up message into a caller's conversation. Limits, enforced by fixed rules before any model is asked (principle VI): a missing or wrong token; a message that is too large or holds nothing Freyja can read (text only in this version); more tasks in progress than a caller's limit or the total limit; an unknown or foreign task or conversation. Each is refused with the protocol's own error and says nothing of what exists for other callers. A loop between Freyja and an agent it hands work to, when that agent also calls Freyja, is recorded as a known limit, with a hop count carried in message metadata as a partial guard. Out of scope: authentication for Freyja's own API and console; callers managed from the console (tokens come from the environment in this version); push notifications; files, images, or structured data in a message; a caller deciding a proposal; discovery or registration of Freyja with other agents; other kinds of credential than a bearer token; changes to the calling agents themselves. Independent of feature 006 (credentials Freyja presents to agents it calls), but a caller's token follows the same rule for what a token may look like. Every existing behavior and test stays as it is when the feature is off."

## Clarifications

### Session 2026-11-25

- Q: When a caller's task leads Freyja to hand work to one of its own delegate agents, should that hand-off wait for a person's approval even when the delegate agent is set to run without approval? → A: Yes, always. Every message to a delegate agent from a caller's thread pauses for a person, whatever the agent's approval choice (FR-013a). The agent's choice deciding as elsewhere, and a setting per caller, were considered and not adopted.
- Q: Freyja keeps working files in one workspace that every task shares. Which files should a caller's task be able to read and write? → A: A named caller's tasks work in a file area of that caller's own, shared by its conversations: they reach no other file, and can read the skills and not change them. Agents on the service's machine that call without a token keep the shared workspace (FR-009a). An area for the local caller too, and the shared workspace for every caller, were considered and not adopted.
- Q: When a caller sends a message without asking for a stream, how long should Freyja hold the answer back? → A: Until the task has ended or a limit has passed, 30 seconds by default and configurable, whichever comes first; after the limit the answer is the task as still working, and the caller reads it again or subscribes (FR-011). Waiting until the task ends however long it takes, and always answering at once, were considered and not adopted.
- Q: When the service is restarted in the ordinary way while a caller's task is running, what should happen to the task? → A: As for a console task today: the run stops between two steps, the caller sees the task as canceled with the reason that the run was stopped before it finished, and nothing is run again by itself; the caller sends another message in the conversation to continue (FR-016, Edge Cases). Continuing by itself after the restart, and reporting the task as failed, were considered and not adopted.
- Q: Callers on other hosts send their token to the outside listener over the network. Who encrypts that connection? → A: The deployment, in front of the listener. The service serves the outside listener without encryption of its own, and logs a warning when it starts with an address for callers whose scheme does not encrypt (FR-029). The service encrypting the connection itself with a certificate it is given, and refusing to start without an encrypting address, were considered and not adopted.

### Plan, 2026-11-25

Changes made while the feature was planned; the plan's "Changes to the spec" gives the reason for each.

- FR-026a names two errors for a message that is refused for another reason than its content type, where it named one: one for what is wrong with the message itself, and one for "not now", so that a caller can tell a message that will never be taken from one to send again.
- FR-016 and a new edge case say when a delegate agent's task counts as awaited. One that waits for input, and whose question Freyja has reported, does not: the received task completes with that reply, and the caller answers with another message.
- FR-017 bounds how many streams follow one task at once: four.
- FR-022a adds that an approval or an edit is refused while a proposal waits to be rejected by rule.
- A new edge case says what a cancel does to a proposal a subagent made: nothing of it runs, and the subagent's step completes before the run stops.

## User Scenarios & Testing *(mandatory)*

Earlier features use these terms, and they keep their meaning here: a **thread** is one conversation the service keeps; the console calls it a **task** (feature 007); what a delegate agent works on for Freyja is an **agent task** (features 003 and 007); a **proposal** is an action that waits for a person's decision. Six terms are new. A **caller** is an agent that hands Freyja work over A2A. A **named caller** is one the deployment named, with a token. The **local caller** stands for every agent that calls on the service's own address without a token. A **conversation** is what the protocol calls a context: the messages one caller sends under one conversation id, kept in one thread. A **received task** is what the protocol calls a task: one message of a caller's and everything Freyja does about it, until it has ended. The **outside listener** is the second address the service can listen on, for callers on other hosts. A named caller's **file area** is the part of Freyja's workspace its runs work in. In the console, a conversation is one task, like any thread, and each received task is one more message on it.

### User Story 1 - An agent hands Freyja a task and reads the result (Priority: P1)

A person who runs Freyja beside another agent on one machine turns the feature on. The other agent reads Freyja's card at the service's own address, learns what Freyja is and how to send it a message, and sends one. Freyja starts working on it as it would on a task a person handed it in the console. The agent follows the task: it sees that Freyja is working, which steps complete, and Freyja's reply as it is written, and when the task has ended it reads the reply as the task's result.

**Why this priority**: This is the feature. Until now Freyja can only be handed work by a person in the console or by a program written against Freyja's own API; an agent that speaks A2A cannot use it. Everything else here builds on one message becoming one task with one result.

**Independent Test**: Turn the feature on with nothing else configured. With a stand-in caller built from the protocol's own client, read the card at the service's own address, send a message that needs no approval, and ask for the stream. The stream shows the task working, a status update for each of Freyja's steps, the reply in pieces, and the task completed with the reply as its result. Send another message without asking for a stream and read the task afterwards: the same result. The console's Tasks section lists both, each marked as started by the local caller. Turn the feature off and restart: the card and every A2A operation answer as any unknown address does, and everything else behaves as before.

**Acceptance Scenarios**:

1. **Given** the feature is on, **When** an agent asks for Freyja's card at the service's own address, **Then** it receives a card that names Freyja, describes what it does, gives the address to send messages to, says that streaming is offered and that push notifications are not, and says that no credential is asked for there.
2. **Given** the feature is on, **When** an agent sends a message with text and no credential to the service's own address, **Then** a received task is made for the local caller, a new thread is started with that text as its first message, and a run starts on it of the kind the console starts.
3. **Given** a message that asks for a stream, **When** the run goes on, **Then** the caller receives, in order: the task as working, a status update for each of Freyja's own steps as it completes, Freyja's reply in pieces as it is written, and the task as completed with the whole reply as its result.
4. **Given** a message that does not ask for a stream, **When** the task ends within the answer wait limit, **Then** the answer is the completed task with its result; when it does not, the answer is the task as it then stands, and the run goes on.
5. **Given** a received task whose stream the caller stops reading, **When** the caller goes away, **Then** the run goes on to its end, and the task can be read afterwards with its result.
6. **Given** a received task in progress or ended, **When** its caller reads it, **Then** the answer gives its state as it is now, and its result once it has ended.
7. **Given** a run that fails, as when no usable model is active, **When** the caller follows or reads the task, **Then** the task is failed with a reason in the service's own words, and the thread and the console hold the reason as they do for any run.
8. **Given** the feature is off, **When** anything asks for the card or sends an A2A operation, **Then** the service answers as it does for an address it does not have, and no thread, task, or log line about a caller is made.
9. **Given** a received task, **When** a person opens the Tasks section, **Then** the conversation is listed as a task like any other, with the caller's message as its first message, and is marked as started by that caller.

### User Story 2 - A person decides what a caller's task proposes (Priority: P2)

A caller's task reaches an action that needs approval: a message to a channel, a hand-off to a delegate agent that requires it, anything with effects outside Freyja's workspace. The run pauses exactly as a run a person started would. The task appears in the console among those that need a decision, marked with the caller that started it, and a person approves, edits, or rejects there. The caller is told that its task is still being worked on and waits for a person's approval, and which actions wait, and nothing more. Nothing the caller can send decides the proposal.

**Why this priority**: The approval gate is the constitution's first principle and the reason Freyja can be trusted with effects on other systems. A way in for other agents that weakened it would be worse than no way in. This story makes the first one safe to turn on.

**Independent Test**: Configure a delegate agent that runs without approval. Send a message from a stand-in caller that leads to a hand-off to it: the run pauses all the same, and the agent has received nothing. Then send a message from a stand-in caller that leads to an action needing approval. The caller sees the task as working, with a status message that says it waits for a person's approval and names the action, without its arguments. Every operation the caller has is tried against the task: none changes the proposal, and the action has not run. In the console, the task is counted among those that need a decision and its page says which caller started it; approve there, and the caller sees the task go on and complete with Freyja's reply. Repeat with a rejection: the action never runs, and the caller sees Freyja's reply to the rejection as the result.

**Acceptance Scenarios**:

1. **Given** a caller's run that reaches an action needing approval, **When** the run pauses, **Then** no part of the action has run, the thread holds the proposal as for any run, and the console counts the task among those that need a decision.
2. **Given** such a paused task, **When** its caller follows or reads it, **Then** the task is working, and its status message says that it waits for a person's approval and names each action that waits, with no argument of any action.
3. **Given** a delegate agent whose approval choice is to run without approval, **When** a run on a caller's thread proposes a message to it, **Then** the run pauses for a person's decision as for an agent that requires approval, and nothing is sent until a person approves or edits.
4. **Given** such a paused task, **When** its caller sends a message that names the task, a message in the same conversation, or any other operation but a cancel, **Then** the proposal is unchanged, no action runs, and a message is refused with the protocol's own error.
5. **Given** such a paused task, **When** a person opens it in the console, **Then** the page and the proposal's card say that the run was started by that caller and not by a person, and the person can approve, edit, or reject as for any proposal.
6. **Given** a person approves or edits, **When** the run continues, **Then** the action runs once, with the arguments the person decided, and the caller sees the task go on and end as any received task does.
7. **Given** a person rejects, **When** the run continues, **Then** the action does not run, and the caller receives Freyja's reply to the rejection as the task's result; it is not told who decided or why beyond what Freyja's reply says.
8. **Given** a caller's task in the console, **When** a person looks for the box that sends another message, **Then** there is none, the page says that only the caller continues its conversation, and a message sent to that thread through the service's own API is refused.
9. **Given** a caller's run in progress, **When** a person presses Stop in the console, **Then** the run stops between two steps as any console run does, and the caller sees the task as canceled.
10. **Given** a paused task, **When** hours or days pass before a person decides, **Then** the task is still working for its caller, can still be read, and continues when the decision comes.

### User Story 3 - An agent on another host calls with its token (Priority: P3)

A person who deploys Freyja lets agents on other hosts hand it work. They name each caller with a token, turn the outside listener on at an address and port of its own, and say which address callers reach it under. A caller on another host reads the card there, which says that a bearer token is asked for, and sends its messages with its token. Nothing else of Freyja can be reached at that address: not the threads, not the agents, not the LLM profiles, not the console.

**Why this priority**: Freyja's own API has no authentication and stays on its own machine. The outside listener is what lets a deployment open exactly one narrow, authenticated way in. It comes third because a deployment where the agents share a machine already works with the first two stories.

**Independent Test**: Configure two named callers with recognizable tokens and the outside listener. From a stand-in caller: read the card at the outside listener without a token; send a message with the first caller's token and follow the task to its result; send one with no token, one with a wrong token, and one with a token in another place than the authorization header: each is refused and makes nothing. Ask the outside listener for every other route the service has: each answers as an unknown address does. Read the first caller's task with the second caller's token: it is answered as a task that does not exist. Start the service with the outside listener on and no caller named: it does not start, and the error names the setting.

**Acceptance Scenarios**:

1. **Given** the outside listener is on, **When** anything asks it for the card, **Then** the card is given without a token, names the address the deployment configured for callers, and says that a bearer token is asked for.
2. **Given** a named caller, **When** it sends an A2A operation to the outside listener with its token in the authorization header, **Then** the operation is carried out for that caller.
3. **Given** the outside listener, **When** an A2A operation arrives with no token, with a token no caller has, or with a token anywhere but the authorization header, **Then** it is refused before anything else is looked at, nothing is made or changed, the refusal is the same in each case, and it does not repeat the token.
4. **Given** the outside listener, **When** anything asks it for a route of the service that is not the card or the A2A operations, **Then** it answers as it does for an address it does not have, the health check included.
5. **Given** the service's own address, **When** an A2A operation arrives there with a named caller's token, **Then** it is carried out for that caller; with no token, for the local caller; and with a token no caller has, it is refused as at the outside listener.
6. **Given** the outside listener is on, **When** the service starts with no caller named, with no address for callers configured, or with the feature itself off, **Then** it does not start, and the error names the setting and no token.
7. **Given** a caller's entry whose name or token breaks the rules, or two callers with one name or one token, **When** the service starts, **Then** it does not start, and the error names the setting and the caller, never a token.
8. **Given** the address configured for callers does not encrypt the connection, **When** the service starts, **Then** it starts and logs a warning that tokens sent there can be read on the network path.
9. **Given** a page of another origin, open in a browser, **When** it sends an A2A operation to either address, **Then** the operation is refused as the thread routes refuse it (feature 007), and the page can read no answer.

### User Story 4 - Continue a conversation, come back to a task, or cancel it (Priority: P4)

A caller sends another message in a conversation it started, and Freyja answers with the whole conversation in mind, as it does for a follow-up in the console. A caller that lost its connection, or that was restarted, reads its task again or subscribes to it again and finds it where it stands, also after Freyja itself was restarted. A caller that no longer wants a task cancels it: Freyja stops between two steps, and a proposal that was waiting for a person is rejected, so that nobody approves an action whose requester is gone.

**Why this priority**: These make the first story dependable over hours and days, which is how long a task with an approval in it lasts. They come fourth because one message with one result is already useful without them.

**Independent Test**: Complete a received task, then send another message under the same conversation id: a new received task, the same thread, and a reply that shows Freyja kept the first exchange in mind. Send a third while the second is in progress: refused. Start a long task, drop the stream, restart the service, and subscribe again: the task is found, and its end is received. Cancel a task whose run is in progress during a tool step: the step completes, the run stops there, and the task is canceled. Cancel one that waits for approval: the thread shows the proposal rejected with the reason that the requesting agent canceled, the action never runs, and the console no longer counts the task among those that need a decision.

**Acceptance Scenarios**:

1. **Given** a conversation whose last received task has ended and whose thread has nothing in progress, pending, or awaited, **When** its caller sends another message under the same conversation id, **Then** a new received task is made, the message is added to the same thread, and Freyja's run has the earlier messages of the conversation in mind.
2. **Given** a conversation with a received task that has not ended, or whose thread still has a run in progress, a proposal pending, or an agent task awaited after a cancel, **When** its caller sends another message under that conversation id, **Then** it is refused with the protocol's own error, and nothing is added to the thread.
3. **Given** a message that names a received task, **When** it arrives, **Then** it is refused, whether or not that task has ended: a received task takes one message.
4. **Given** a message that names no conversation, **When** it is accepted, **Then** Freyja gives the conversation an id of its own and returns it with the task.
5. **Given** a received task that has not ended, **When** its caller subscribes to it, **Then** the caller receives the task as it stands and every update from then on, to its end.
6. **Given** a received task, **When** the service is restarted, or the operation reaches another instance sharing the database, **Then** the task can be read, subscribed to, and canceled as before, with the same id, state, and result.
7. **Given** a received task whose run is in progress, **When** its caller cancels it, **Then** the step under way completes, the run stops before the next one, the task is canceled, what the run did so far stays in the thread, and the task stays canceled also when the run ended by itself before the stop took effect.
8. **Given** a received task that waits for a person's approval, **When** its caller cancels it, **Then** every action of the pending proposal is rejected with the reason that the requesting agent canceled, none of them runs, the run that records the rejection stops at its first boundary, the task is canceled, and the thread and the console show the proposal as rejected by the caller's cancel and not by a person.
9. **Given** a received task that waits for a delegate agent's task, **When** its caller cancels it, **Then** the received task is canceled, the agent task goes on, and its outcome is recorded in the thread when it comes, as today, without reopening the received task; a proposal the run that records it comes to is rejected by rule, with the reason that the requesting agent canceled.
10. **Given** a cancel that arrives while a step is under way whose reply proposes an action needing approval, **When** the run pauses on that proposal instead of stopping, **Then** the proposal is rejected as in scenario 8, and the task is canceled.
11. **Given** a received task that has ended, **When** its caller cancels it or subscribes to it, **Then** the operation is refused with the protocol's own error and the task is unchanged.
12. **Given** a cancel and a person's decision that arrive at the same moment, **When** both are handled, **Then** exactly one of them takes effect: either the decision is applied and the cancel then stops the continuation between two steps, or the proposal is rejected by the cancel and the decision is refused as one for a proposal that is no longer pending.

### User Story 5 - A caller sees only what is its own, and no more than it should (Priority: P5)

A caller learns the state of its own tasks, the names of the steps Freyja took, and Freyja's own reply. It never learns another caller's tasks or that they exist, anything from a thread or a file of the console's or of another caller's, where a delegate agent is, or any credential. What the service itself tells it of a step is a name, never an argument, a result, or a delegate agent's words; what Freyja chooses to say of its own work in its reply is Freyja's reply. A deployment bounds how much a caller can ask of Freyja at once, and each bound is a fixed rule applied before any model is asked anything.

**Why this priority**: It protects the four stories before it and adds no capability of its own. It is required before the outside listener is opened to anything.

**Independent Test**: Configure two named callers with recognizable tokens, a delegate agent at a recognizable address, and an LLM profile with a recognizable key. Drive every operation as each caller, refusals included, through tasks that complete, pause, fail, and are canceled, with a tool whose arguments and result hold a recognizable text and a delegate agent whose reply does, and with a file of a recognizable name and text written by a console task and by each caller's task. Search everything either caller received: no token, no key beyond what feature 004 allows, and no address. Search every status update and every reason: no argument, no result, and no text of the delegate agent's. As each named caller, ask Freyja to list and read every file it can and to change a skill: it finds its own file and neither of the others, and no skill is changed. Search everything the service returned elsewhere, kept in a thread, and logged at any level: no token. Ask as the second caller for every task and conversation of the first: each answer equals the answer for an id that was never used. Send messages past each limit: each is refused before the stand-in model is asked anything.

**Acceptance Scenarios**:

1. **Given** two callers, **When** one reads, subscribes to, cancels, or sends a message under a task or a conversation id of the other's, **Then** a task operation is answered exactly as for an id that does not exist, and a message under the other's conversation id starts a conversation of the sender's own, in a thread of its own.
2. **Given** a thread started in the console or through the service's own API, **When** any caller uses an id from it, **Then** nothing of it can be read, continued, or stopped through A2A.
3. **Given** a received task whose run uses tools and delegate agents, **When** its caller receives status updates, **Then** each names the tools or agents the step used and nothing of their arguments, their results, or the agent's own words.
4. **Given** Freyja's reply, **When** it reaches a caller, in pieces or whole, **Then** it holds no stored API key beyond what feature 004 allows and no delegate agent's address, as for anything the service returns.
5. **Given** a named caller, **When** a run on its thread lists, reads, writes, or deletes files, **Then** it reaches the caller's own file area and nothing else of the workspace: no file of the console's tasks or of another caller's, and it can read the skills and cannot change them.
6. **Given** a run that fails with an error a model endpoint or a library supplied, **When** the caller reads the task, **Then** the reason it is given is one of a fixed set of sentences in the service's own words, and none of the supplied text.
7. **Given** a named caller's token, **When** anything is returned, streamed, logged at any level, or kept in a thread, **Then** it holds nothing of the token.
8. **Given** a message whose text is longer than the limit, holds no text, or holds something that is not text, **When** it arrives, **Then** it is refused with the protocol's own error, names the rule, and starts nothing.
9. **Given** a caller with as many received tasks that have not ended as its limit allows, or the service with as many as the total limit allows, **When** another message arrives, **Then** it is refused with one reason for both, that a limit on tasks in progress was reached, and starts nothing.
10. **Given** a message that says it has passed through as many hand-overs between agents as the limit allows, or whose count is not a whole number of zero or more, **When** it arrives, **Then** it is refused and starts nothing.
11. **Given** a run on a caller's thread that hands work to a delegate agent, **When** the message is sent, **Then** it carries the number of hand-overs so far, one more than the caller's message carried.

### Edge Cases

- **A received task hands work to a delegate agent, and the agent task is still pending when the run ends.** The received task stays working, with a status message that names the agent it waits for. When the outcome is recorded in the thread and Freyja has replied to it, in the run the service starts by itself for that (feature 003), the received task ends with that reply as its result. That run's reply reaches the caller when the run ends at the latest; it need not be streamed in pieces.
- **A cancel rejects a proposal that a subagent of Freyja's made.** No action of the proposal runs. The subagent works inside one step of Freyja's, so it is told of the rejection and may go on until that step is done, as any step under way completes when a stop is asked; the run stops at the first boundary of Freyja's own steps. A proposal the subagent comes to meanwhile is rejected in the same way.
- **A delegate agent asks a question.** Its task waits for input, and Freyja reports the question in a run of its own, as today (feature 003). Once that run has ended, the agent task is no longer awaited: the received task completes with Freyja's reply, which carries the question, and the caller answers with another message in the conversation, which Freyja can pass on to the agent, with a person's approval. Otherwise the task would wait for an answer its caller is not allowed to send while it works.
- **The service is stopped in the ordinary way while a caller's run is in progress.** The run a message or a decision in the console started is a console run, and is asked to stop at its next boundary (feature 007). The caller sees the task as canceled, with the reason that the run was stopped before it finished. Nothing is run again by itself after the restart; the caller continues with another message in the conversation, and Freyja has what the stopped run did in mind. A task that waits for a person or for a delegate agent has no run in progress and is not touched by a restart.
- **A run the service started by itself on a caller's thread, to report a delegate agent's outcome, is cut off, fails, or is given up.** Such a run is not a console run and ends as it does today (feature 003). The received task does not stay working for it: once nothing of the thread is in progress, pending, or awaited, the task ends, as failed with the reason that the run was interrupted when the last run did not finish.
- **A continuation fails while its proposal is still pending,** as when no usable model is active at the moment a person approves. The proposal is what the thread needs (feature 007), so the received task is still working and waits for a person; it has not failed.
- **A cancel finds a proposal for which a person's decision was already taken, and whose action has not run yet.** A cancel never undoes a person's decision and never carries one out. The proposal stays as the person left it, the task ends as canceled, and the console says on the task that the requesting agent canceled, so that a person who continues it knows.
- **A decision on a caller's proposal is sent through the service's own API, in the way that ends when its client stops reading (feature 001).** It is applied as today. The run it starts cannot be stopped by a cancel; the task is canceled all the same, and what that run does is left in the thread.
- **The service is killed during a caller's run.** Once it runs again, the task is reported as failed, with the reason that the run was interrupted. Nothing is run again by itself.
- **A person stops a caller's run, or rejects its proposal, in the console.** A stop gives the caller a canceled task. A rejection is a decision like any other: the run continues, and the caller receives Freyja's reply. The caller is not told that a person did either.
- **A caller subscribes through another instance than the one that drives the run.** It receives the task as it stands, each change of its state, its status message as it changes, and its result. The steps and the reply in pieces are sent by the instance that drives the run, to the callers that follow the task there; through another instance they may be missing, and what the caller is told is never wrong, only less.
- **A caller reads a stream too slowly.** A reader that falls too far behind is disconnected, as a console page is (feature 007). The run goes on, and the caller reads the task or subscribes again.
- **Two messages arrive at the same moment under one new conversation id, from one caller.** One starts the conversation. The other is refused as a message to a conversation with a task that has not ended. No second thread is made.
- **Two callers choose the same conversation id.** Each has its own conversation and its own thread. A conversation id means something only together with its caller.
- **Several agents call on the service's own address without a token.** They are one caller, the local caller: each can read, continue, and cancel what another of them started. An agent on this machine that is to be kept apart is given a name and a token and presents it there. That keeps it apart over A2A only: anything on the service's machine can still list every thread, read it, and decide its proposals through the service's own API, as before this feature.
- **A caller has the same name as a delegate agent.** The two are unrelated. A name among callers gives nothing among delegate agents, and the other way round; the console says "started by" for the one and lists agent tasks for the other.
- **A caller's limit is reached by tasks that wait for a person.** A received task counts from the moment it is accepted until it has ended, also while it waits for approval or for a delegate agent. A caller whose tasks all wait is refused more until one is decided, canceled, or ended.
- **A caller's entry is removed from the configuration.** After the restart that applies it, the token is refused. The caller's conversations stay in the console as tasks, with the name they were started under; a run in progress when the service stopped was stopped with it. A caller named again later under the same name has those conversations again.
- **A caller's token is replaced.** After the restart, the new token gives the same caller the same conversations, and the old one is refused.
- **No usable model is active.** A message is accepted and its task fails at once with that reason, as a console task does; nothing is queued for later.
- **A caller asks for the result in a form Freyja does not produce.** The result is text. A message that accepts only other forms is refused with the protocol's own error.
- **A caller asks for push notifications, or for the extended card.** Refused with the protocol's own error for an operation that is not offered. The card says that neither is.
- **A caller sends a message that asks Freyja to approve its own proposal, or says that a person approved.** It is text, like any message. Nothing in a message, a status, or a metadata field is ever read as a decision.
- **Freyja hands work to an agent that hands work back to Freyja.** The hand-over count stops such a loop when both sides carry it on. An agent that drops it starts from nothing. On Freyja's side every hand-off from a caller's thread waits for a person (FR-013a), so a loop cannot turn without one; what the other agent does by itself is bounded by the limits on tasks in progress. This is a known limit.
- **A caller sends the same message twice because it did not see the answer.** Two received tasks are made, unless the second meets the refusal of a conversation with a task that has not ended. Freyja does not recognize a repeated message.
- **The outside listener's address is taken, or cannot be listened on.** The service does not start, and the error names the setting.
- **A caller subscribes to, or reads, a task while the answer to its own message has not arrived yet.** The task exists from the moment the message is accepted, and is answered as it stands.
- **A thread a caller started is opened through the service's own API.** Its state can be read and its proposal decided there, as the console does. A message to it is refused there too (User Story 2, scenario 8).

## Requirements *(mandatory)*

### Functional Requirements

**Turning it on, and who may call**

- **FR-001**: The service MUST be able to receive work from other agents over the A2A protocol: it serves a card that describes it and the protocol's operations of FR-007. This MUST be off by default. With it off, the service MUST behave as it did before this feature in every respect, the card and the operations MUST answer as an address the service does not have, and every automated test that existed before MUST pass unchanged.
- **FR-002**: With the feature on, the card and the operations MUST be served at the service's own address. There, an operation that carries no token MUST be carried out for the local caller, one that carries a named caller's token for that caller, and one that carries a token no caller has MUST be refused as FR-005 says. Which of the two addresses a request arrived at is decided by the listener that accepted its connection, never by anything the request says of itself. Every rule that keeps a web page of another origin and a request made for an unknown host name from the service's own API (features 005 and 007, and the rule added after them) MUST hold for the card and the operations there.
- **FR-003**: A deployment MUST be able to turn on an outside listener, off by default, at an address and a port of its own that have no default. It MUST serve the card and the A2A operations and nothing else: every other route of the service, the health check and the console's forwarding included, MUST answer there as an address the service does not have. It MUST start and stop with the service, in whatever way the service is started, and differ between deployments by configuration alone. A deployment MUST also say under which address callers reach it; the service cannot know. The outside listener on while the feature is off, with no caller named, or with no address for callers MUST stop startup with an error that names the setting.
- **FR-004**: A deployment MUST be able to name callers, each with a name and a token. They are deployment configuration: read from the environment when the service starts, none by default, documented with the service's other settings, and not changeable while the service runs or through any route. A name is in the form agents' names have (lowercase letters, digits, hyphens, and underscores, starting with a letter, at most 32 characters), MUST differ from every other caller's, and MUST NOT be `local`. A token follows the rule feature 006 gives a token (16 to 4,096 visible ASCII characters) and MUST differ from every other caller's. At most 20 callers MAY be named. An entry that breaks these rules MUST stop startup with an error that names the setting and the caller, never a token.
- **FR-005**: At the outside listener, every A2A operation MUST carry a named caller's token in the request's authorization header, as a bearer token. An operation with no token, with a token no caller has, or with a token anywhere else MUST be refused before anything else of the request is looked at, MUST make and change nothing, and MUST be answered the same way in each case, without repeating the token and without saying whether a caller of some name exists. The card MUST be readable there without a token. A token MUST be compared so that the time the comparison takes says nothing of how much of it was right.
- **FR-006**: The card MUST name Freyja, say in the service's own words what it does, and say that streaming is offered and that push notifications and an extended card are not. Read at the service's own address, it MUST give the address it was asked under, which is one the service answers for, and say that no credential is asked for. Read at the outside listener, it MUST give the address the deployment configured for callers and say that a bearer token is asked for. Where the protocol asks a card to list skills, it lists one, general: that Freyja takes a request in plain language. It MUST hold nothing about the deployment beyond that: no delegate agent, tool server, tool, model, profile, or caller.

**What a message does**

- **FR-007**: A caller MUST be able to: send a message, with or without asking for a stream of updates; read one of its received tasks; subscribe to one that has not ended; and cancel one. Push notifications, the extended card, and listing tasks are not offered; asking for one, also as part of a send, MUST be refused with the protocol's own error for an operation that is not offered.
- **FR-008**: A message MUST hold text and nothing else, at least one character that is not blank and at most 32,000 characters in all, the limit the thread routes have. A message that breaks this, or that accepts no text as a result, MUST be refused with the protocol's own error, naming the rule, before a thread or a task is made and before any model is asked anything.
- **FR-009**: A message that names no conversation, or a conversation id its caller has not used, MUST start a conversation: a new thread, whose id the service chooses and which no caller can choose or learn, and a run on it with the message's text, of the kind the console starts (feature 007, FR-021). The run MUST go on to its end whether or not the caller reads it, and everything that holds for a console run MUST hold for it: one run per thread on every instance, the step limit, the approval gate, the record of each completed step, and a stop only between two steps. When the message names no conversation, the service MUST make an id and return it. A conversation id a caller supplies MUST be at most 128 characters.
- **FR-009a**: A run on a named caller's thread MUST work in that caller's own file area. It MUST NOT be able to list, read, write, or delete a file of the console's tasks, of the service's own API's threads, or of another caller's, and it MUST be able to read the skills and MUST NOT be able to change them. The area is the same for all of that caller's conversations and is kept across restarts. The local caller's runs work in the workspace every thread shares today, as a thread started through the service's own API does.
- **FR-010**: A message under a conversation id its caller has used MUST continue that conversation when its last received task has ended and nothing of its thread is in progress, pending, or awaited: a new received task, the message added to the same thread, and a run that has the conversation in mind, as a follow-up in the console does (feature 007, FR-020). While a received task of the conversation has not ended, or its thread still has a run in progress, a proposal pending, or an agent task awaited, the message MUST be refused with the protocol's own error and MUST add nothing to the thread. A message that names a received task MUST be refused, whether or not the task has ended.
- **FR-011**: A send that does not ask for a stream MUST be answered with the received task: at once when the caller asks not to wait, and otherwise when the task has ended or after the answer wait limit, whichever comes first, with the task as it then stands. The limit MUST be configurable, with a default of 30 seconds. Either way the run goes on.
- **FR-012**: A received task MUST be kept so that it can be read, subscribed to, and canceled after a restart of the service and through any instance that shares the database, with the same id, state, status message, and result. Its id MUST be the service's own and MUST NOT be a thread's id. That a caller started a thread, and which, MUST be recorded before the thread's first run starts; when it cannot be recorded, the message MUST be refused and nothing started, so that a caller's thread is never shown or treated as a person's.

**The approval gate**

- **FR-013**: A run on a caller's thread MUST pause on every action that needs approval exactly as any run does, with the proposal kept in the thread and offered in the console (features 001 and 007). No operation a caller has, and nothing a message, a status, or a metadata field holds, MAY approve, edit, or reject a proposal, or cause an action to run that a person has not decided where a decision is required. The one thing a caller can do to a pending proposal is to have it rejected by canceling the task (FR-021).
- **FR-013a**: On a caller's thread, every message to a delegate agent, whether a hand-off, a follow-up, an answer, or a cancel, MUST pause for a person's decision, whatever the agent's approval choice is. An agent's choice to run without approval was made for requests a person makes (feature 005, FR-022); on a caller's thread no person made the request. A tool server's tool that is marked read-only runs without approval as today.
- **FR-014**: While a received task waits for a person's decision, its caller MUST see it as working, with a status message in the service's own words that says it waits for a person's approval and names each action that waits. The message MUST hold no argument of any action. The task MUST stay so for as long as the proposal is pending, with no time limit of this feature's.
- **FR-015**: Only a person MUST be able to decide a proposal of a caller's task, in the console or through the routes the console uses, with every rule a decision has today. A caller MUST NOT be told who decided or why, beyond the task going on, the steps that follow, and what Freyja's reply says.

**What a caller sees**

- **FR-016**: A received task has one of four states for its caller. It is working from the moment its message is accepted and for as long as its thread has a run in progress, a proposal pending, whatever the last run did, or a delegate agent's task awaited. An agent task is awaited while it is working, while its outcome is not in the thread yet, and while a run to report it is still to be tried; one that waits for input and whose question was reported is not. The received task ends when none of the three is left: as completed when the thread's last run ended with a reply of Freyja's; as canceled when that run was stopped between two steps, by a person or because the service was stopping; and as failed when it ended with an error or was cut off. A cancel its caller sent and the service accepted ends it as canceled at once, whatever its run then ends on. A received task MUST NOT stay working once nothing of its thread is in progress, pending, or awaited, and a task that has ended MUST NOT change again. The states the protocol has for a task that needs something from its caller MUST NOT be used.
- **FR-017**: While a caller follows a received task, by the stream of its send or by a subscription, it MUST receive: each change of the task's state; a status update for each step of Freyja's own that completes, saying what kind of step it was and naming the tools and the delegate agents it used; the status messages of FR-014 and of an awaited agent task; and Freyja's own reply in pieces as it is written, for the run the message started and for its continuation after a decision. Pieces MUST be sent only of text the service knows to be Freyja's own reply, never a subagent's; where it cannot tell, the reply is sent whole when its step completes. A caller that follows through another instance than the one that drives the run MUST receive at least each change of state, each change of the status message, and the result. At most four streams MAY follow one task at once; one more is refused as FR-026a says for "not now". When the task completes, its result MUST be Freyja's last reply, whole, as text.
- **FR-018**: Nothing a caller receives, Freyja's reply included, MAY hold: a stored API key beyond what feature 004 allows; a delegate agent's address (feature 005); any caller's token; a thread's id; a proposal's id; or another caller's name, task, or conversation. What the service itself tells a caller, in a status update, a status message, or a reason, MUST also hold no argument or result of a tool or of a message to a delegate agent, nothing a subagent or a delegate agent wrote, and not who decided a proposal. Freyja's reply is Freyja's to word: it reports what the caller's own task did and found, and is not a boundary for that. It is a boundary for everything outside the task, which FR-009a and FR-020 keep out of the run's reach.
- **FR-019**: The reason given to a caller for a failed or canceled task MUST be one of a fixed set of sentences the service words itself: no usable model is active; the model could not be used; the run reached its step limit; the run was interrupted; the run was stopped before it finished; the caller canceled the task; an internal error. It MUST hold no text a model endpoint, a library, a tool, or an agent supplied. The thread and the console keep and show a run's own reason as they do today.
- **FR-020**: A conversation and its received tasks belong to the caller that started them, by name; every agent that calls without a token is the one local caller. An operation on a task id that is not the caller's own MUST be answered exactly as for an id that was never used, in what is returned and in how it is refused. A conversation id is the caller's own to choose, so a message under an id another caller uses starts a conversation of the sender's. No operation MAY read, continue, or stop a thread that was not started by its caller over A2A. This separates callers from each other and from the console over A2A; what the service's own API lets anything on its machine do is unchanged.

**Cancel**

- **FR-021**: A caller MUST be able to cancel a received task of its own that has not ended. An accepted cancel ends the task as canceled for its caller at once, and is answered with the task in that state; what was done so far stays in the thread. What it does to the thread depends on where the thread stands. A run in progress that the console's Stop can stop MUST be stopped as Stop does (feature 007, FR-022): the step under way completes, and no action is cut off. A run in progress of another kind, one the service started by itself or one started through the service's own API, goes on as it would today. When a proposal is pending, or the run that was asked to stop pauses on one, every action of it that no person has decided MUST be rejected with the reason that the requesting agent canceled, none of them MAY run, the run that records the rejection MUST stop at its first boundary, and the thread and the console MUST show the proposal as rejected by the caller's cancel and not by a person. A decision a person already took is never undone and never carried out by a cancel. When a delegate agent's task is awaited, it MUST go on as it is, and its outcome MUST be recorded in the thread as today. A cancel of a task that has ended MUST be refused with the protocol's own error.
- **FR-022**: A cancel and a person's decision that arrive together MUST NOT both take effect on the proposal: either the decision is applied, once, and the cancel stops the continuation between two steps, or the cancel rejects the proposal and the decision is refused as one for a proposal that is no longer pending.
- **FR-022a**: When a run on a caller's thread comes to a proposal and the conversation has no received task that has not ended, as after a cancel, the proposal MUST be rejected by rule, with the reason that the requesting agent canceled, and no action of it MAY run: nobody is asked to approve an action whose requester is gone. Until it is rejected, a request that approves or edits an action of it MUST be refused, with a code of its own, changing nothing; one that rejects is accepted.

**The console**

- **FR-023**: A conversation MUST appear in the console's Tasks section as a task like any other: listed, counted when it needs a decision, opened, followed, decided, and stopped as feature 007 specifies. The list, the task's page, and a proposal's card MUST say that it was started by a caller and which, in words, so that a person who decides knows that no person asked for the action. The local caller MUST be named as an agent on this machine.
- **FR-024**: A message MUST be added to a caller's thread only by its caller over A2A. The console MUST offer no box to send another message on such a task and MUST say why. The service MUST refuse a message sent to such a thread through its own routes, with a code of its own, changing nothing. Reading the thread's state, deciding its proposal, and stopping its run through those routes are unchanged.

**Limits and loops**

- **FR-025**: The number of received tasks that have not ended MUST be limited, for each caller and in all, by two configurable limits with defaults of 5 and 20. A task counts from the moment it is accepted until it has ended, and a canceled one for as long as its thread still has a run in progress or an agent task awaited. A message over either limit MUST be refused, with one reason for both, that a limit on tasks in progress was reached, so that a caller learns nothing of how much others ask; the log says which. The refusal comes before a thread or a task is made and before any model is asked anything. Tasks started in the console or through the service's own API are not counted.
- **FR-026**: Every refusal this feature adds, of a credential, a message's form, a limit, a task or conversation that is not the caller's, an operation that is not offered, and a hand-over count, MUST be decided by a fixed rule on the request and on what the service has stored, never by a model, and before any model is asked anything.
- **FR-026a**: Each refusal MUST be answered in one named way, the same every time. A credential that is missing or wrong: the answer the protocol's HTTP binding gives a request without valid credentials, before anything of the protocol is read. A task that is not the caller's, or that does not exist: the protocol's error for a task that is not found. A cancel or a subscription of a task that has ended, and an operation that is not offered: the protocol's errors for those. A message that is not text, or that takes no text as a result: the protocol's error for a content type that is not supported. What is wrong with a message itself, whatever the service is doing, its length, no text, a task it names, its conversation id, or its hand-over count: the protocol's error for parameters that are not valid, with a reason from a fixed set of sentences in the service's own words. What is refused only for now, a conversation that takes no message, a limit on tasks in progress, or on the streams of one task: the protocol's error for an operation that is not supported, with a sentence of the same fixed set and a reason code, so that a caller can tell a message to send again from one that will never be taken.
- **FR-027**: A message MAY say how many hand-overs between agents it has passed through; one that does not has passed through none. A count that is not a whole number of zero or more, and one that has reached the limit, configurable with a default of 3, MUST be refused. Every message Freyja sends to a delegate agent from a thread a caller started MUST carry the count of the conversation's last message from its caller, plus one. The count is carried where the protocol lets a message carry data of its sender's choosing, under a name the documentation gives.

**What is logged, kept, and tested**

- **FR-028**: The service MUST log, naming the caller and never a token: each received task that was accepted, with its id and its thread; each cancel; each operation refused for its credential, as a warning; each message refused for a limit; and, when it starts, that the feature is on, whether the outside listener is, and the warning of FR-029. A caller's token MUST appear in no log line at any level, no answer, no stream, and no thread.
- **FR-029**: The service does not encrypt the connection itself; a deployment that opens the outside listener puts what encrypts in front of it. When the address configured for callers has a scheme that does not encrypt, the service MUST start and MUST log a warning that tokens sent there can be read on the network path.
- **FR-030**: The README MUST document how to turn the feature on, how to name a caller, how to open the outside listener and what it serves, what a caller can and cannot do, how an approval looks to a caller and where a person decides it, that a send which does not ask for a stream can be answered with a task that is still working, a named caller's file area, that every message to a delegate agent from a caller's thread waits for a person, the limits, and the hand-over count's name. Every new setting MUST be documented with the service's other settings.
- **FR-031**: The service's behavior and the console's behavior MUST each be covered by automated tests that need no network and no agent installed or running, with a stand-in caller built from the protocol's own client in a caller's place. The console's part of every user story MUST also be covered by an end-to-end test that drives the console in a browser. The tests MUST include: a search for a recognizable caller's token in everything the service returns, streams, keeps, and logs at any level; a search of everything a caller received for an argument, a result, a delegate agent's words, an address, and a key; every operation tried by one caller against another's task; a named caller's run trying to reach files outside its area and to change a skill; every operation tried against a pending proposal; a message to an agent that runs without approval, shown to pause on a caller's thread; and each refusal of FR-026 shown to be made before the stand-in model is asked anything.

### Key Entities

- **Caller**: An agent that hands Freyja work. A named caller has a name and a token, both from the deployment's configuration; the local caller has neither and stands for every agent that calls on the service's own address without a token. Known in the console by its name.
- **Caller's token**: The credential a named caller presents. It comes from the environment, is compared and never shown, and appears in nothing the service returns, streams, keeps, or logs.
- **Conversation**: The messages one caller sent under one conversation id. It belongs to that caller, is kept in one thread, and is one task in the console.
- **Received task**: One message of a caller's and what Freyja does about it. It has an id of the service's own, a state (working, completed, failed, or canceled), a status message, and, once completed, a result: Freyja's last reply. It is kept across restarts and shared by every instance.
- **File area**: The part of the workspace a named caller's runs work in. It is that caller's own, shared by its conversations, and apart from the workspace other threads share.
- **Card**: What Freyja says of itself to an agent that asks: its name, what it does, where to send messages, what it offers, and whether a token is asked for at the address it was read from.
- **Outside listener**: A second address the service can listen on, which serves the card and the A2A operations to callers that present a token, and nothing else.
- **Thread** (features 001 and 007): gains which caller started it, when one did. A thread a caller started takes messages from that caller only.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An agent that speaks A2A and runs on the service's machine can hand Freyja a task and read its result after one setting is turned on. No code is changed, and nothing else is configured.
- **SC-002**: With the feature off, every automated test that existed before this feature passes unchanged, and the card and every A2A operation answer as an address the service does not have.
- **SC-003**: In 100% of automated runs, an action that needs approval in a caller's task, every message to a delegate agent among them, has not run when the task pauses, runs at most once and only after a person approved or edited it in the console, and never runs after a rejection or a cancel. Zero operations available to a caller change a pending proposal other than by canceling its task.
- **SC-004**: A person deciding a proposal can tell from the proposal's card alone, in 100% of automated runs, that a caller started the run, and which.
- **SC-005**: In 100% of automated runs, an operation at the outside listener without a named caller's token in the authorization header makes and changes nothing, and every route of the service other than the card and the A2A operations answers there as an address the service does not have.
- **SC-006**: A recognizable caller's token appears in nothing the service returns, streams, keeps in a thread, or logs at any level, through every operation, refusals included.
- **SC-007**: Across every operation, one caller receives nothing of another caller's tasks or conversations, and nothing of a thread started in the console: each answer about an id that is not its own equals the answer about an id that was never used, in 100% of automated runs. A named caller's run reaches zero files outside its own area and changes zero skills.
- **SC-008**: Nothing a caller receives holds a delegate agent's address, a stored API key beyond what feature 004 allows, or text a model endpoint or a library supplied in an error, and no status update or reason holds an argument or a result of an action or a delegate agent's own words, in 100% of automated runs.
- **SC-009**: A caller that follows a task through the instance that drives its run sees a reply Freyja writes by itself begin before the reply is complete, and sees a step named within two seconds of the step completing.
- **SC-010**: After the service is restarted, 100% of received tasks can be read with the same id, state, and result as before, and a task that had not ended can be subscribed to and canceled.
- **SC-011**: In 100% of automated runs, a cancel never cuts off an action under way, and a canceled task that waited for approval leaves a proposal that no person can approve.
- **SC-012**: In 100% of automated runs, a message refused for its form, a limit, or its hand-over count starts no thread, no task, and no request to a model.
- **SC-013**: A caller on another host can be given access by setting three things: its name and token, the outside listener's address, and the address callers reach it under.
- **SC-014**: No received task stays working once nothing of its thread is in progress, pending, or awaited, in 100% of automated runs, including after a run the service started by itself was cut off, failed, or was given up.

## Assumptions

**Scope**

- Out of scope, per the description: authentication for Freyja's own API and console; callers managed from the console; push notifications; files, images, or structured data in a message or in a result; a caller deciding a proposal; discovery or registration of Freyja with other agents; other kinds of credential than a bearer token; and changes to the calling agents themselves.
- Also out of scope: the extended card; listing a caller's tasks; a caller reading a conversation's earlier messages back; a token that differs per conversation or per request; more than one token per caller; replacing a caller or a token without a restart; rate limits and lockouts for wrong tokens, which a deployment applies in front of the outside listener; the service encrypting the outside listener's connection itself; deleting received tasks or conversations; running a task again by itself after the service was stopped or killed; changing the card's text from the configuration; and versions of the protocol other than the one Freyja reaches its own delegate agents with (feature 003).
- This feature specifies Freyja's side only. An agent that is to call Freyja has to speak the protocol as a client and, on another host, present a bearer token. ARTEX and heimdall were looked at on 2026-11-25: both serve the protocol in the version Freyja reaches them with, and neither has a client of its own yet, so no earlier version is needed, and giving either one a client is that agent's own work.
- The console is in English and is used with a current desktop browser, as before.

**Behavior choices**

- Callers and their tokens are deployment configuration, not operator-managed configuration (FR-004). The list decides who can make the service act from another host. If it could be changed through the service's own unauthenticated API, it would decide nothing. Feature 006 puts the hosts agents may be reached at in the environment for the same reason. Because they are read at startup and never stored, feature 004's secret is not needed for them.
- Two ways in, and the service's own API stays where it is (FR-002, FR-003). An agent on the service's machine can already start a run through the thread routes, so asking it for a token would protect nothing. An agent on another host must not be given the service's unauthenticated API along with A2A, so it gets a listener that serves A2A alone. Opening the service's own address to other hosts and protecting only the A2A routes there was considered and not adopted: everything else on that address would be open with it.
- A token is honored at the service's own address too (FR-002). It lets a deployment tell two agents on one machine apart, in the console and in what each can read. Without one, agents there are one caller.
- A caller never sees a proposal as something to answer (FR-014, FR-016). The protocol has a state for a task that needs input from its caller. Using it for an approval would invite the caller to answer, and an agent's answer is exactly what principle I does not accept. The task is working, and the status message says what it waits for. The owner chose this on 2026-11-25; showing the state for input, and letting the caller decide, were considered and not adopted.
- A caller is told the names of tools and delegate agents and nothing they were given or returned (FR-017, FR-018). The owner chose step names on 2026-11-25, so that a caller can tell a task that moves from one that is stuck. Names tell a caller what the deployment has; a deployment that names a caller accepts that.
- A caller is given fixed reasons, not a run's own error (FR-019). A model endpoint's error can hold what the endpoint was sent. The console still shows it to the operator, cleaned as today.
- A received task stays working while its thread waits for a delegate agent's task (FR-016, Edge Cases). A caller wants the result of what it asked for, and Freyja's first reply in that case is only that work was handed on. Ending the task with that first reply was considered and not adopted.
- A cancel ends the task for its caller at once, whatever the thread still does (FR-016, FR-021). A caller that cancels wants no result, and a run that completes by itself a moment later does not make the cancel untrue. The thread keeps what happened.
- A cancel rejects a pending proposal (FR-021). Otherwise a person could approve, days later, an action nobody is waiting for. A rejection has no effect outside Freyja, so the cancel decides nothing that principle I reserves for a person. Leaving the proposal pending, and refusing a cancel while one is pending, were considered and not adopted.
- Only the caller adds messages to its conversation (FR-024). Freyja's next reply to the caller is written with the whole thread in mind, so a message an operator typed there could reach the caller in Freyja's words. A person still decides and stops.
- A conversation is the caller's own id together with the caller's name (FR-020). Nothing a caller chooses becomes an id in Freyja's own API, and two callers that choose one id never meet.
- A send that does not ask for a stream waits at most the answer wait limit (FR-011). A task with an approval in it can take days, and no request should be held open that long. A caller that needs the end reads the task or subscribes, as Freyja itself does with a delegate agent's pending task (feature 003). This departs from a reading of the protocol in which such a send waits for the task's end; the task it returns says truthfully that it is working. Confirmed in clarification on 2026-11-25; waiting for the task's end however long it takes, and always answering at once, were considered and not adopted.
- An ordinary restart cancels a caller's running task, and nothing continues by itself (FR-016, Edge Cases). It is what a console task does today (feature 007), where a person continues with another message; a caller does the same. Continuing a run by itself after a restart would be the first thing Freyja runs again unasked, and would need rules of its own for a run that fails each time. Confirmed in clarification on 2026-11-25; continuing by itself, and reporting the task as failed, were considered and not adopted.
- One reason for both limits (FR-025). A refusal that named the total limit would tell a caller how busy the others are.
- A received task counts against the limits while it waits for a person (FR-025). It holds a thread, a proposal a person must look at, and possibly a delegate agent's work. A caller that fills its limit with waiting tasks is held back until people have caught up.
- The hand-over count is a partial guard, and a known limit is recorded (FR-027, Edge Cases). It rests on the other agent carrying it on. With FR-013a a loop through Freyja needs a person's approval at every turn, so the count matters most for what the other side does without one.
- A caller's message is a request like a person's, with two differences (FR-009, FR-009a, FR-013a). Freyja works on it with the same tools and limits, behind the same approval gate, which the caller cannot pass. What a caller can cause with no person involved is what Freyja does without approval: read-only tools, and files in the workspace.
- A named caller's runs work in a file area of its own (FR-009a). Today every thread shares one workspace, and reading and writing there needs no approval. Without a separate area, a caller could ask Freyja to read the files of the console's tasks and of other callers', and to change the skills every later run loads; FR-020 would then hold for ids and not for content. The local caller keeps the shared workspace, since an agent on the service's machine can already start a thread there through the service's own API. Confirmed in clarification on 2026-11-25; giving every caller the shared workspace, and giving the local caller an area too, were considered and not adopted.
- Every message to a delegate agent from a caller's thread waits for a person (FR-013a). An operator who lets an agent run without approval chose that for requests people make. With a caller, the same hand-off would be asked for, sent, and answered with no person anywhere, and two such agents could hand work back and forth without end. The cost is a click for every hand-off a caller's task leads to. Confirmed in clarification on 2026-11-25; letting the agent's approval choice decide as elsewhere, and a setting per caller, were considered and not adopted.
- The deployment encrypts the way to the outside listener, and the service warns when the address for callers does not (FR-029). A proxy, an ingress, or a mesh in front of a service is where a deployment keeps its certificates, and a certificate in the service would be one more thing to renew by a restart. A closed network or a test setup without encryption stays possible, with the warning. Confirmed in clarification on 2026-11-25; the service encrypting the connection itself, and refusing to start without an encrypting address, were considered and not adopted.
- The outside listener answers under any host name (FR-003). The rule that holds the service's own API to the names it answers for exists because that API takes requests without a credential, which a web page under a hostile name could send. At the outside listener every operation needs a token no web page has, and the card is public.
- Trust, as far as it changes. The deployment is trusted to name callers, to keep their tokens, and to put encryption and rate limits in front of the outside listener. A named caller is trusted to hand Freyja work within its limits and with nothing more: it cannot approve, cannot read what is not its own, and cannot reach anything but A2A. An agent on the service's machine is trusted as before, since it could already use the whole API. The operator is trusted as in feature 007, and now also sees and decides what callers' tasks propose.

**Earlier requirements this feature changes**

- Feature 005, FR-022: an agent's approval choice is the only thing that decides whether a message to it pauses, except on a caller's thread, where every such message pauses (FR-013a). It is only ever stricter there.
- Features 001 and 002, the one workspace every thread works in: a named caller's threads work in an area of their own, and cannot change the skills (FR-009a).
- Feature 007, FR-020: a task's page has a box to send another message, except for a task a caller started (FR-024).
- Feature 007, FR-027, and feature 001: a message sent to a thread through the service's own routes is accepted as before, except to a thread a caller started (FR-024). No thread that exists before this feature is one.
- Feature 007, the list of tasks and a task's row: each gains which caller started the thread, when one did (FR-023).
- Features 003 and 005: a message Freyja sends to a delegate agent from a thread a caller started carries a hand-over count (FR-027). Messages from every other thread are sent as before.
- The constitution's statement that the server binds the local address unless configured otherwise holds: the outside listener is off unless configured, and has no default address.

**Environment and dependencies**

- This specification is written against the service as it is with features 001 to 005 and 007 complete. Feature 008 (progress of pending agent tasks) is being built and feature 006 (remote agents with a credential) is specified and not planned; neither is needed here. If feature 006 changes its rule for a token before it is built, the rule of FR-004 follows it.
- The constitution needs no amendment. Principle I holds as written: the gate, its three decisions, and who decides do not change, and a paused run is resumable after any delay. Principle II has agents reached over A2A; this feature has Freyja reached the same way. Principle III keeps one runtime: the outside listener is part of the same service and differs by configuration. Principle IV puts what a deployment needs before it can start in the environment, with safe local defaults. Principle VI is what FR-026 applies.
- The run a caller's message starts, and the continuation a decision in the console starts, are console runs in the sense of feature 007, so that feature's rules for a run without a reader, for Stop, and for the service stopping apply to them without change. A run the service starts by itself on a caller's thread to report a delegate agent's outcome, and one started through the service's own API, stay what they are today; FR-016 and FR-021 say what a received task does around them.
- The stand-in model and the stand-in agent of earlier features play the model and the delegate agents in the automated tests. The caller is played by the protocol's own client library.
- Several service instances sharing one database are assumed to be given the same callers, tokens, and limits. The service does not detect a difference.
