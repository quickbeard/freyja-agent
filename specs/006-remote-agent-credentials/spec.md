# Feature Specification: Delegate Agents on Other Machines, with a Credential

**Feature Branch**: `006-remote-agent-credentials`

**Created**: 2026-11-19

**Status**: Draft

**Input**: User description: "Delegate agents on other machines, with a credential. Until now an agent Freyja hands work to must run on the same machine as the service: an address that is not this machine's is refused, and an agent whose card declares any authentication is refused, because the link to an agent carries no credential and so is only safe over loopback. That fits a developer's machine and breaks once Freyja is deployed, where an agent runs as a service of its own, in another container or on another host. This feature lets a deployment name the hosts on which agents may be reached, and lets each agent have a credential, a bearer token, that Freyja presents with every request to it. An agent's address is accepted when it is on this machine, as today, or when its host is one the deployment allows; the list of allowed hosts is deployment configuration read from the environment, is empty by default, and with it empty the service behaves exactly as it does today. The rule is the same for an agent named in FREYJA_A2A_AGENTS and for an agent an operator saved through the console (feature 005). An agent may have a token. For an environment agent it comes from the environment. For a saved agent the operator enters it in the Agents section when adding or changing the agent; it is stored encrypted under the service's secret key as stored LLM API keys are (feature 004), is never returned, shown, logged, or written to a thread beyond its last four characters, and the form keeps nothing once sent or closed; the operator can replace it or remove it. An agent whose card asks for a bearer token can be used when Freyja has a token for it, and is refused with the reason when it has none; a card that asks for any other kind of authentication is still refused. The token is sent only to the agent's configured host and port, never to an address taken from its card or from a redirect, and never to an agent that did not ask for one. When an agent refuses the token, the agent is listed as unreachable with that reason, a hand-off to it becomes an error result naming the agent, and nothing is retried. Everything else about an agent is unchanged whether it is local or remote: its approval choice is still the only thing that decides whether a message to it pauses for a person, its address is still kept out of everything the orchestrator sees and out of every thread, log line, and catalog entry, and two agents still cannot share one address, where a remote address now counts its host as well as its port and path. Out of scope: authentication for Freyja's own API and console, which stay unauthenticated and are not exposed beyond the service's own machine; other kinds of credential (OAuth flows, API keys in other schemes, client certificates, mutual TLS); custom certificate authorities; rotating tokens automatically; discovering agents; and the agent's own side of the link, meaning how an agent checks the token it is sent. This specification is written as if feature 005 (the Agents section of the web console) were complete, since it will be planned and built after 005 is finished."

## User Scenarios & Testing *(mandatory)*

This specification is written as if feature 005 were complete. Its terms are used as they are there: an **environment agent** is one named in `FREYJA_A2A_AGENTS`, a **saved agent** is one an operator added through the console, and an agent's **approval choice** says whether messages to it require a person's approval. Four terms are new. A **local** address is one on the service's own machine, the only kind accepted until now; a **remote** address is any other. An **allowed host** is a host the deployment has named as one agents may be reached on, with or without a port. An agent's **token** is the credential Freyja presents to it. A card **asks for a bearer token**, **asks for no credential**, or **asks for another kind of credential** as FR-012 defines.

### User Story 1 - Hand work to an agent that runs somewhere else (Priority: P1)

A person who deploys Freyja runs an agent as a service of its own, in another container or on another host. They name that host in the deployment's configuration as one agents may be reached on, name the agent in `FREYJA_A2A_AGENTS` with its address there, and give the service the token the agent expects. The service starts, reads the agent's card, and the orchestrator can hand work to the agent as it does to a local one: a hand-off pauses for approval unless the entry says otherwise, and once approved the agent receives the message, with the token.

**Why this priority**: This is what a deployment needs and cannot have today. Until now the only way to put Freyja and an agent in one deployment is to run them as one unit that shares a loopback interface, which also lets the agent reach Freyja's own unauthenticated API. Everything else in this feature builds on an agent being reachable elsewhere.

**Independent Test**: Start a stand-in agent that asks for a bearer token, under a host name that is not this machine's. Configure the service with that host allowed, the agent named in the environment at that address, and the token. Start the service and send a message that leads to a hand-off. The run pauses; approve it and confirm from the stand-in's own record that it received exactly that message, with the token, at its own address. Remove the host from the allowed hosts and restart: the service refuses to start and names the agent.

**Acceptance Scenarios**:

1. **Given** a host named as allowed and an environment agent at an address on that host, **When** the service starts, **Then** it reads the agent's card at that address, the orchestrator and its subagent have the agent's two tools, and the catalog lists the agent with no address.
2. **Given** such an agent whose card asks for a bearer token, and a token configured for it, **When** a hand-off to it is approved, **Then** the agent receives the message with the token, and the result reaches the orchestrator as for a local agent.
3. **Given** such an agent, **When** the orchestrator, its subagent, or a background run proposes a hand-off, a follow-up, an answer, or a cancel to it, **Then** whether the run pauses is decided by the agent's approval choice alone, exactly as for a local agent.
4. **Given** an environment agent at a remote address whose host is not allowed, **When** the service starts, **Then** startup fails with an error that names the agent and the rule, and not the address.
5. **Given** no allowed host is configured, **When** the service starts with any configuration that was valid before this feature, **Then** it behaves as it did, apart from what FR-028 lists, and an agent at a remote address is refused as it was.
6. **Given** a remote agent with a task pending, **When** the service watches the task, **Then** each check carries the token when the agent's card asked for one, and the outcome is reported in the thread as for a local agent.
7. **Given** a remote agent that is down when the service starts, **When** the service starts, **Then** it starts, warns, and lists the agent as unreachable, as feature 005 specifies for any agent.

### User Story 2 - A token goes to the agent it belongs to, and nowhere else (Priority: P2)

An agent that asks for a token gets the one configured for it, on every request, and only at its own address. An agent that asks for none is sent none. When a token is missing, or the agent refuses it, or the agent asks for a kind of credential Freyja does not have, the operator is told which of these it is, in the service's own words, and no message is lost silently: the hand-off becomes an error result and the run continues.

**Why this priority**: A credential that can be sent to the wrong place is worse than none. This story is what makes the first one safe to rely on, and it is specified by itself so that every way a token could leave its agent has a requirement and a test.

**Independent Test**: With three stand-in agents on an allowed host: one that asks for a bearer token and is given the right one, one that asks for one and is given a wrong one, and one that asks for none while a token is configured for it. The first receives the token on every message, check, and cancel. The second is listed as unreachable with the reason that it refused the credential, and a hand-off to it gives an error result. The third never receives a token, by its own record. A fourth stand-in whose card points its interface at another host or another scheme, and one that answers with a redirect, never cause the token to be sent anywhere but the configured scheme, host, and port.

**Acceptance Scenarios**:

1. **Given** an agent whose card asks for a bearer token and a token configured for it, **When** the service sends it a message, an answer, or a cancel, or reads a task's status, **Then** each of those requests carries the token.
2. **Given** an agent whose card asks for no credential, **When** a token is configured for it, **Then** no request to it carries the token, the agent can be used, and its card in the console says the token is not used.
3. **Given** an agent whose card asks for a bearer token, **When** no token is configured for it, **Then** the agent cannot be used and the reason says that it asks for a credential and none is configured.
4. **Given** an agent whose card asks for any other kind of credential, **When** its card is read, **Then** the agent cannot be used and the reason says that it asks for a kind of credential Freyja does not have, whether or not a token is configured.
5. **Given** an agent that refuses the token it is sent, **When** a hand-off, an answer, a cancel, or a check of a task meets that refusal, **Then** the agent is listed as unreachable with the reason that it refused the credential, a hand-off, an answer, or a cancel becomes an error result naming the agent, the run continues, the refused request is not sent again, and the service stops reading that agent's tasks by itself until FR-017 lets it try again.
6. **Given** an agent whose card names an interface on another host or port, or with another scheme, **When** the service sends a request, **Then** the request and the token go to the configured scheme, host, and port, as every request does today.
7. **Given** an agent that answers a request with a redirect, **When** the service receives it, **Then** the redirect is not followed and the token is not sent to where it points.
8. **Given** an agent's card, **When** the service reads it, **Then** the request for the card carries no token.
9. **Given** an agent whose card cannot be read without a credential, **When** the card is requested, **Then** the agent cannot be used and the reason says so.
10. **Given** a token, **When** any request carries it, **Then** it is carried in the request's authorization header and never in an address.
11. **Given** an agent whose card asks for no credential, **When** it refuses a request for lack of one, **Then** the agent is listed as unreachable with the reason that it asks for a credential its card does not declare, and no token is sent to it.
12. **Given** an agent with tasks pending, **When** it asks for a bearer token and none can be presented, because none is configured or the stored one cannot be read, **Then** no request is made for those tasks, and they stay pending until a token can be presented or they reach the maximum age.

### User Story 3 - Add a remote agent, with its token, from the console (Priority: P3)

An operator adds an agent in the Agents section whose address is on an allowed host, and enters the token the agent expects. The agent is saved and usable from the next run, as feature 005 specifies. The card in the console shows that the agent has a token, and its last four characters, and nothing more of it. Later the operator replaces the token, or removes it, from the same form.

**Why this priority**: It brings to saved agents what the first two stories give environment agents. It comes third because a deployment can already be run with environment agents alone, and because it adds the one new place where a token is typed, stored, and shown.

**Independent Test**: With a host allowed and the stand-in agent that asks for a token running there, add it through the console with its address and token. Its card shows that it has a token ending in the right four characters; a hand-off to it is approved and reaches the stand-in with the token. Replace the token with a wrong one: the next hand-off gives an error result, and the card says the agent refused the credential. Put the right one back: hand-offs work again. Try to add an agent on a host that is not allowed: refused at the address, and nothing is saved. Restart the service: the agent and its token are still there.

**Acceptance Scenarios**:

1. **Given** the form for adding an agent, **When** it opens, **Then** it has a field for a token, empty, beside the fields feature 005 gives it, and what is typed there is not shown as readable text.
2. **Given** an address on an allowed host where an agent that asks for a bearer token can be used, and its token, **When** the operator saves, **Then** the agent is saved, its card shows the address, that it has a token, and the token's last four characters, and the next run can hand work to it.
3. **Given** an address whose host is neither this machine nor allowed, **When** the operator saves, **Then** nothing is saved and the form says at the address that the host is not one this deployment allows.
4. **Given** an agent whose card asks for a bearer token, **When** the operator saves with the token field empty, **Then** nothing is saved and the form says that the agent asks for a credential.
5. **Given** a saved agent with a token, **When** the operator opens it to change it, **Then** the token field is empty, the form says that a token is stored and shows its last four characters, and saving without typing one keeps the stored token.
6. **Given** a saved agent, **When** the operator types a new token and saves, **Then** the new token replaces the stored one, and requests made by runs that start afterwards carry the new one.
7. **Given** a saved agent with a token, **When** the operator removes the token and confirms, **Then** the agent has none; when its card asks for one, the confirmation said the agent cannot be used without it, and the agent is listed as unreachable with that reason until a token is entered. Unlike an add, a removal reads no card, so it is not refused.
8. **Given** a token was typed into the form, **When** the form is sent successfully or closed, **Then** nothing of the token is kept in the page.
9. **Given** a saved agent with a token, **When** the Agents section lists it or answers a change of it, **Then** the answer says whether the agent has a token and carries the last four characters, and never the token.
10. **Given** the secret that protects stored credentials is not set, **When** the operator saves an agent with a token, **Then** nothing is saved and the form names the missing setting; an agent with no token can still be saved.
11. **Given** a saved agent, **When** the service restarts, **Then** the agent is listed with the same token, and requests to it carry it.
12. **Given** several service instances share one database, **When** a token is added, replaced, or removed through one of them, **Then** a run that starts on any instance afterwards uses the token as it is now.
13. **Given** a saved agent with a token, **When** its address is changed to another scheme, host, or port and the request gives no token, **Then** the stored token is discarded with the change, the confirmation said so, and the agent has none at its new address; a request sent straight to the service behaves the same.
14. **Given** a saved agent with a token, **When** only the path of its address is changed, **Then** the stored token is kept.

### User Story 4 - Tokens and remote addresses stay where they belong (Priority: P4)

Nothing the service returns, streams, logs, or keeps in a thread holds a token beyond its last four characters, and nothing outside the Agents section holds a remote agent's address, its host included. A person reading a thread, the catalog, a run's stream, or the service's log learns which agent was used, and never where it is or what opens it.

**Why this priority**: It protects the three stories before it and adds no capability of its own. It is still required before anything that carries a token is released.

**Independent Test**: Configure one environment agent and one saved agent on an allowed host with a recognizable host name, each with a recognizable token. Drive every route of the Agents section with them, refusals included, with runs that complete, pause, and fail, with an agent that refuses its token and one that repeats it in its error, a check, a change of token, and a removal. Search every response, every stream, every thread, the catalog, and everything the service's process logged at any level: neither token appears beyond its last four characters, anywhere; the host name appears in the Agents section's answers about the saved agent and, apart from what an agent wrote in its own replies, nowhere else.

**Acceptance Scenarios**:

1. **Given** an agent with a token, **When** anything about it is returned, streamed, logged, or kept, **Then** it holds at most the token's last four characters, and those only where the Agents section says the agent has a token.
2. **Given** an agent that repeats the token in an error or in a reply, **When** that text reaches a thread, a stream, a log line, or a reason, **Then** the token has been removed from it.
3. **Given** a saved agent at a remote address, **When** anything outside the Agents section's own answers mentions the agent, **Then** it holds neither the address nor its host, apart from what the agent wrote in its own replies and progress updates, which are not searched for an address (feature 005, FR-028).
4. **Given** an environment agent at a remote address, **When** anything about it is returned, the Agents section included, **Then** it holds neither the address nor its host.
5. **Given** a failure to reach a remote agent, such as a name that cannot be resolved or a certificate that is not trusted, **When** the failure is reported, **Then** the report names the agent and the kind of failure, in the service's own words, and holds neither the host nor the token.
6. **Given** a request to the Agents section that carries a token, **When** it is refused for any reason, **Then** the refusal does not repeat the token.
7. **Given** a page served from another origin, **When** it asks for the agents or tries to change one, **Then** it can read no response, token indications included, and nothing changes, as feature 005 specifies.

### Edge Cases

- **A host is removed from the allowed hosts while agents use it.** The list is read when the service starts. After the restart that applies the change, an environment agent on that host is an invalid entry and stops startup, naming the agent, as any address that is not accepted does. A saved agent on that host is listed as not in use with the reason, its pending tasks are given up as at a removal, and the only thing the operator can do with it is remove it, as feature 005 specifies for a saved agent the environment overrides. When the host is allowed again, the saved agent is in use again as it was saved.
- **An allowed host's name resolves to this machine, or to somewhere the deployment did not intend.** The service compares names as they are written and does not look them up to decide. A name the deployment lists is the deployment's to vouch for. One consequence is stated plainly: a listed name that reaches this machine gives a local agent a second address, which the rule that two agents cannot share an address does not catch.
- **The list names this machine, or an address that is nowhere in particular.** An entry that is `localhost`, a loopback address, the unspecified address, or a link-local address is refused, and the service does not start. This machine is already accepted without the list, and the others are never an agent's.
- **A host is written in another spelling.** Capitals and one trailing dot are ignored, an IP address is compared by its value however it is written, and a name written in another alphabet is compared in the form it is sent in. An address and a list entry that differ in any other way are different hosts.
- **An allowed host is listed without a port.** Every port of that host is accepted. Anyone who can reach the console can then make the service request a card from any port there and learn which kind of failure it met, as feature 005 already allows for this machine's ports. A deployment that wants less lists the host with its port.
- **An address names its host by IP address.** It is accepted when that IP address is on the list, written the same way. An IP address is not accepted because a listed name resolves to it.
- **Two agents are saved under two names for one remote host.** The rule that two agents cannot share an address compares remote hosts as written. Two names that reach one host are not detected, as two paths that reach one interface are not in feature 005.
- **The token is sent over an address that is not encrypted.** The address's scheme is the operator's choice and is used as written. Over a remote address without encryption, anyone on the path can read the token. The service accepts it, says so in a warning in its log when it starts with such an agent, and the console says so before such an agent is saved; a deployment that allows a host vouches for the path to it.
- **An agent's certificate is not trusted, or does not match its host.** The agent cannot be reached, and the reason says that its certificate was not accepted. There is no setting that skips this check, and no way to add a certificate authority in this feature.
- **An agent stops asking for a token, or starts asking for one, after it was configured.** The card is read again whenever the service connects to the agent: when it starts or learns of the agent, after a failure to reach it, and at an operator's check (feature 005). What the card asks for then decides. An agent that now asks for a token while none is configured cannot be used, with the reason. One that no longer asks is no longer sent its token.
- **An agent's card asks for a bearer token and for another kind of credential, as alternatives.** The bearer token is enough. When the card asks for both together, the agent cannot be used.
- **The secret that protects stored credentials was changed.** A saved agent's stored token cannot be read. The service starts, lists the agent as unreachable with the reason that its stored credential cannot be read, and lets the operator enter the token again or remove the agent. Saved agents without a token, and environment agents, are not affected.
- **A token is replaced while a run is in progress.** The run finishes with the token it started with. When the agent no longer accepts that one, the run's remaining messages to it become error results, as for any refused credential.
- **A token is replaced or removed while a hand-off waits for a decision.** Continuing a paused run starts it anew with the agents as they then are (feature 005, FR-019), so an approval sends the message with the token as it is then. With none, when the agent asks for one, the message is not sent and the call gives an error result.
- **Something else answers at an agent's address after the agent's card was read.** It is sent the token with the next request. A token is as safe as the deployment's control over what answers at the agent's address; reading the card first lowers the chance of handing a token to a mistyped address, and is not a boundary.
- **A task of an agent asks for authentication of its own while it runs.** As today: the task ends as failed with the reason that it asks for authentication, whether or not the agent has a token (feature 003).
- **An environment agent's address carries a user name or a password.** Feature 003 accepts that for a local address, and it stays accepted there for an agent with no token. For an agent that has a token, or whose address is remote, such an address is an invalid entry and stops startup: two credentials for one agent would leave which one is sent to chance.
- **A saved agent with a token is moved.** A token was entered for one place. When the scheme, the host, or the port of the address changes, the stored token is discarded unless the same change gives a token, and the confirmation says so; when only the path changes, it is kept. Otherwise anyone who can reach the console could move an agent to a listener of their own and be sent its token.
- **A local agent asks for a token.** It is treated as a remote one is: local or remote decides only whether the address needs an allowed host.
- **An environment entry gives a token that is empty or not in the allowed form.** It is an invalid entry and stops startup with an error naming the agent, and not the token.
- **Several instances are given different allowed hosts or different tokens for an environment agent.** Each instance decides from its own configuration. An instance that does not allow a saved agent's host lists it as not in use and gives up its pending tasks, for every instance, as feature 005 specifies when instances are given different environments. The service does not detect this.
- **An agent on an allowed host is reached through a proxy the environment configures.** It is not: requests go to the agent's host and port directly, as feature 005 specifies. A deployment where agents can only be reached through a proxy is out of scope.
- **An operator enters a token that is very long or holds characters that cannot be sent.** It is refused with the rule, and nothing is saved.

## Requirements *(mandatory)*

### Functional Requirements

**Where an agent may be**

- **FR-001**: A deployment MUST be able to name hosts on which agents may be reached. The list is deployment configuration: read from the environment when the service starts, empty by default, documented with the service's other settings, and not changeable while the service runs. An entry is one host, written as a name or as an IP address, optionally followed by one port, without a scheme, a path, or a pattern that stands for several hosts. An entry MUST NOT be this machine (`localhost` or a loopback address), the unspecified address, or a link-local address. At most 50 entries MAY be given. A list that breaks these rules MUST stop startup with an error that names the setting and not the entry.
- **FR-002**: An agent's address MUST be accepted when its host is this machine, under the rule that applies today (`localhost` or a loopback IP address), or when its host is on the list: an entry with a port accepts that port only, and an entry without one accepts every port. Hosts are compared as written, with three allowances: capitals are ignored, one trailing dot is ignored, and an IP address is compared by its value, however it is written. A name in another alphabet is compared in the form it is sent in. Any other address MUST be refused. The service MUST NOT look a name up to decide whether an address is accepted. The rule is the same for an environment agent and for a saved agent, and every other rule about the form of an address (feature 005, FR-006) is unchanged.
- **FR-003**: With no host named, the service MUST behave as it did before this feature for every configuration that was valid before it, apart from what FR-028 lists, and an agent at a remote address MUST be refused as it was.
- **FR-004**: An environment agent whose address is not accepted is an invalid entry: it MUST stop startup with an error that names the agent and the rule and does not repeat the address, as today. A saved agent whose address is not accepted MUST be refused when it is added or moved, with nothing saved. A saved agent whose host is no longer on the list when the service starts MUST NOT be used: the service MUST start, MUST list the agent as not in use with the reason, MUST give up its pending tasks as at a removal, and MUST let the operator remove it and do nothing else with it. When the host is on the list again at a later start, the agent is in use again as it was saved.
- **FR-005**: Two agents MUST NOT share an address (feature 005, FR-006). For an address on this machine the comparison is the one feature 005 defines: the port and the path, however this machine is written. For a remote address it is the host, compared as FR-002 compares hosts, the port, and the path. A remote address and a local one never count as the same.

**The token**

- **FR-006**: An agent MAY have one token. A token is 16 to 4,096 characters, each a visible ASCII character: no space and no control character. A value that breaks this rule MUST be refused naming the rule, never the value.
- **FR-007**: An environment agent's token MUST come from the service's environment. It MUST NOT be part of the agent's address: an environment agent that has a token, or whose address is remote, and whose address carries a user name or a password, is an invalid entry. An entry whose token is empty or breaks FR-006 is an invalid entry too. An invalid entry MUST stop startup with an error that names the agent and never the token or the address.
- **FR-008**: An operator MUST be able to enter a token for a saved agent when adding it or changing it, to replace a stored token, and to remove it. A saved agent's token MUST be stored so that it cannot be read from the stored agent without the secret the operator gives the service through its configuration, the same secret that protects stored LLM API keys (feature 004, FR-020). It MUST be the same for every service instance sharing the database and MUST survive a restart.
- **FR-009**: When that secret is not set, saving an agent with a token MUST be refused with a reason that names the missing setting; saved agents without a token, and environment agents, MUST keep working. When a stored token cannot be read with the current secret, the service MUST start, MUST list the agent as unreachable with that reason, and MUST let the operator enter the token again or remove the agent.
- **FR-010**: Replacing or removing a saved agent's token is a change of the agent in the sense of feature 005: it is made from the values the page last read and refused when they are no longer current (005, FR-012), it takes effect for runs that start afterwards on every instance (005, FR-019), and the console asks for confirmation before a removal. It MUST NOT give up the agent's pending tasks, and by itself it MUST NOT contact the agent, so a removal is not refused because the agent's card asks for a token: the confirmation MUST say that such an agent cannot be used without one. A run in progress keeps the token it started with; a paused run that is continued afterwards starts with the token as it then is.
- **FR-011**: A saved agent's token belongs to the place it was entered for. A change of address that changes the scheme, the host, or the port MUST discard the stored token unless the same request gives a token, whether the request comes from the console or is sent straight to the service; a change of the path alone keeps it. The confirmation for a change of address MUST say which of the two will happen. No sequence of requests MAY cause a stored token to be presented at a scheme, host, or port other than the one it was entered for.

**When a token is sent**

- **FR-012**: An agent can be used when its card asks for no credential, or asks for a bearer token and a token is configured for the agent. This replaces the rule that a card declaring anything about credentials cannot be used (feature 005, FR-007). What a card asks for is read from the requirements it states, for the agent as a whole and for each of its skills; a kind of credential the card describes and does not require counts for nothing. A requirement is a set of alternatives. An alternative is met with a bearer token when it names exactly one kind of credential and that kind is a bearer token sent in the authorization header; it is met with nothing when it names none. The card asks for no credential when every requirement it states, or none stated at all, can be met with nothing. It asks for a bearer token when every requirement can be met with nothing or with a bearer token, and at least one cannot be met with nothing. In every other case it asks for another kind of credential, and the agent cannot be used: a user name and password, a key in another place, a sign-in flow, a certificate, or a bearer token together with anything else.
- **FR-013**: Every request the service makes to an agent whose card asks for a bearer token MUST carry the agent's token: a message, an answer, a cancel, and the reading of a task's status. A request to an agent whose card asks for no credential MUST NOT carry a token, whether or not one is configured. The request that reads an agent's card MUST NOT carry a token.
- **FR-014**: A token MUST be sent only to the scheme, host, and port of its agent's address: never to an address taken from the agent's card, whatever scheme, host, or port the card names, never to where a redirect points, which is not followed, as today, and never to another agent. It MUST be carried in the request's authorization header and MUST NOT appear in any address the service requests.
- **FR-015**: What a card asks for is decided each time the service reads the card to connect to the agent, which feature 005 has it do when it starts or learns of the agent, after a failure to reach the agent, and at an operator's check. An agent that comes to ask for a token while none is configured cannot be used from then on, with the reason; an agent that no longer asks for one is no longer sent it. The service MUST NOT ask an agent for any other card than the one it serves to everyone.

**When something is wrong**

- **FR-016**: To the fixed reasons feature 005 gives for an agent that cannot be used (005, FR-016), this feature adds, each in a sentence the service words itself: the agent asks for a credential and none is configured; the agent asks for a kind of credential Freyja does not have; the agent's card cannot be read without a credential; the agent refused the credential; the agent's stored credential cannot be read; the agent's certificate was not accepted; the agent's host is not one this deployment allows; and the agent asks for a credential its card does not declare. The second replaces feature 005's reason for a card that requires authentication. An agent with any of these reasons is listed in the state feature 005 calls unreachable, or not in use for a host that is not allowed (FR-004), with the reason. No reason holds a token, an address, or text supplied by an agent or a library.
- **FR-017**: When an agent refuses the token, the service MUST list the agent as unreachable with that reason and the time, a hand-off, an answer, or a cancel that met the refusal MUST become an error result naming the agent, the run MUST continue, and the refused request MUST NOT be sent again. The same holds, with its own reason, when an agent whose card asks for no credential refuses a request for lack of one. From then on the service MUST NOT read that agent's tasks by itself, so that a refused token is not presented again every round: the tasks stay pending, and reading resumes once the agent's token was replaced, a message a run sent to the agent was accepted, or the service restarted. When an agent asks for a bearer token and none can be presented, because none is configured or the stored one cannot be read, no request other than the reading of its card MAY be made to it, and its tasks stay pending. Tasks that stay pending are given up at the maximum age, as today.
- **FR-018**: An address whose scheme encrypts the connection MUST be verified against the certificate authorities the service's machine trusts, so that an authority the deployment installed on the machine is honored, and against the host in the address. A connection that fails that verification MUST NOT be used, and no setting MAY turn the verification off.
- **FR-019**: When an agent with a token has a remote address whose scheme does not encrypt the connection, the service MUST log a warning that names the agent when it starts and when it learns of such an agent, and the console MUST ask for confirmation before such an agent is saved or such a token is entered, saying that the token will be sent where others on the network path can read it. A request sent straight to the service is accepted without that confirmation, and the warning is logged.

**What is shown, and what is not**

- **FR-020**: The service MUST never return a token, and MUST never write one to a log, a thread, or a stream. The most it shows of a token is whether the agent has one and its last four characters, and those only in the Agents section's own answers. For an environment agent the Agents section says whether it has a token and shows its last four characters as well. A refusal of a request that carried a token MUST NOT repeat it.
- **FR-021**: Text about an agent that is shown, logged, or kept, including a reason, an error result, an error an agent or a library supplied, and an agent's replies and progress updates, MUST have that agent's token removed from it. Removal means the token's exact text within one piece of text the service handles, such as one error, one reply, or one progress update; an encoded or altered form, and a token an agent spreads over several pieces, are not searched for (feature 004, FR-021).
- **FR-022**: The Agents section MUST show, for each agent, whether it has a token, whether its card asks for one, and, when a token is configured that the card does not ask for, that the token is not used. The form for a saved agent MUST never be filled with a stored token: it says that one is stored, shows its last four characters, and keeps the stored one when the field is left empty. A token typed into the form MUST NOT be shown as readable text, and nothing of it MUST be kept once the form is sent successfully or closed.
- **FR-023**: Everything feature 005 requires about an agent's address (005, FR-028) holds for a remote address. In addition, wherever an address must be removed, a remote address's host by itself MUST be removed as well, since for a remote agent the host is what tells where it is. It is removed where it stands as a whole name, not where it is part of a longer name or word, and removing it MUST NOT remove the agent's own name from text the service words itself, also when the two are the same word. What an agent writes in its own replies and progress updates is still not searched for an address. A saved agent's remote address is returned by the Agents section's own routes and by nothing else; an environment agent's is returned by nothing.

**What does not change**

- **FR-024**: An agent's approval choice MUST remain the only thing that decides whether a message to it pauses for a decision (feature 005, FR-022). Whether an agent is local or remote, and whether it has a token, MUST NOT influence it. Every rule of feature 005 about runs in progress, pending proposals, and pending tasks applies to a remote agent as to a local one.
- **FR-025**: Every request to an agent MUST go to the host and port of its address, directly, and never through a proxy the environment configures (feature 005, FR-027). By itself the service MUST contact an agent only to read its card and the status of a pending task; adding, changing, and checking an agent read its card and nothing more, so they report whether a token is needed and present, and not whether the agent accepts it.
- **FR-026**: The routes of the Agents section stay closed to pages of other origins, and the console stays unframable, as feature 005 specifies (005, FR-029). The service's own API and console stay unauthenticated.
- **FR-027**: The service MUST log, naming the agent and never its address or its token: that a token was added, replaced, or removed for a saved agent; each request an agent refused because of its credential; each agent that cannot be used for a reason of FR-016, as a warning, at startup and when the service finds it out; and the warning of FR-019.

**Compatibility and quality**

- **FR-028**: With no allowed host and no token configured, every behavior of the service MUST be what it was when feature 005 was complete, and every automated test that existed then MUST pass, apart from two things that follow from FR-012: a card that asks for a credential is refused with one of the reasons of FR-016 in place of feature 005's one reason, and a card that describes a kind of credential and requires none can now be used.
- **FR-029**: The service's behavior and the web app's behavior MUST each be covered by automated tests that need no network and no agent installed or running, with the stand-in agent in the agent's place, able to ask for a token and to refuse one. The console's part of every user story MUST also be covered by an end-to-end test that drives the console in a browser. The tests MUST include a search for a recognizable token, and for a recognizable remote host, in everything the service returns, streams, keeps, and logs at any level.

### Key Entities

- **Allowed host**: A host the deployment has named as one agents may be reached on, with one port or with every port. It belongs to the deployment's configuration, is read when the service starts, and is never shown or changed through the console.
- **Agent token**: The one credential Freyja presents to one agent. An environment agent's comes from the environment; a saved agent's is entered by an operator and kept so that it cannot be read without the service's secret. Known outside the service only by whether it exists and by its last four characters.
- **Delegate agent** (feature 005): gains whether it has a token, and may now be at a remote address on an allowed host. Its name, approval choice, card details, and reachability are as before.
- **Agent card** (feature 005): now also says whether the agent asks for a bearer token. That decides whether the token is sent, and never anything about approval.
- **Reason an agent cannot be used** (feature 005): the fixed set gains the reasons of FR-016.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A person deploying Freyja can run an agent on another host and have the orchestrator hand work to it by setting three values: the allowed host, the agent's entry, and its token. No code is changed and nothing else is configured.
- **SC-002**: A deployment that names no allowed host and no token behaves as before: every automated test that existed when feature 005 was complete passes, changed only as FR-028 lists.
- **SC-003**: In 100% of automated runs, an agent that asks for a bearer token receives its token on every message, answer, cancel, and status check, by the stand-in agent's own record.
- **SC-004**: In 100% of automated runs, a token reaches nothing but its own agent's scheme, host, and port: zero requests to an address from a card, to a redirect's target, to another agent, or to an agent that asked for no credential carry it, zero requests for a card carry it, and no sequence of changes to a saved agent causes its stored token to be presented at a scheme, host, or port other than the one it was entered for.
- **SC-005**: A recognizable token appears beyond its last four characters in nothing the service returns, streams, keeps in a thread, or logs at any level, through every route of the Agents section and through runs that complete, pause, and fail, including when an agent repeats the token in one piece of its own error or reply.
- **SC-006**: A recognizable remote host appears in nothing the service returns outside the Agents section's answers about a saved agent, streams, keeps in a thread, or logs at any level, apart from what an agent wrote in its own replies and progress updates.
- **SC-007**: In 100% of automated runs, an address whose host is neither this machine nor allowed is refused, for an environment agent at startup and for a saved agent when added or moved, and nothing was requested from that host.
- **SC-008**: In 100% of automated runs, whether a message to an agent pauses is the same for a remote agent as for a local one with the same approval choice, for the orchestrator, its subagent, and a background run.
- **SC-009**: An operator can tell from the Agents section alone, for every agent that cannot be used because of its credential or its host, which of the reasons of FR-016 it is, in 100% of automated runs.
- **SC-010**: An operator who has a remote agent's address and token at hand can add it and have the next run hand work to it in under two minutes, without editing a file and without restarting anything, once its host is allowed.
- **SC-011**: After a restart, saved agents have the same tokens as before it, and after the secret that protects them is changed, the service still starts and every affected agent is listed with the reason, in 100% of automated runs.
- **SC-012**: A token an agent refuses loses no message silently: 100% of the hand-offs, answers, and cancels that meet the refusal give the orchestrator an error result naming the agent, and none is sent twice. After a refusal, the service by itself presents that token to the agent zero more times until one of the three events of FR-017.
- **SC-013**: An agent whose certificate is signed by an authority installed on the service's machine can be reached, and one whose certificate is not trusted or does not match its host cannot, in 100% of automated runs.

## Assumptions

**Scope**

- Out of scope, per the description: authentication for Freyja's own API and console; other kinds of credential (OAuth flows, API keys in other schemes, client certificates, mutual TLS); custom certificate authorities; rotating tokens automatically; discovering agents; and the agent's side of the link, meaning how an agent checks the token it is sent.
- Also out of scope: tool servers reached over an address, which keep their own rule and are not affected by the allowed hosts; a task that asks for authentication of its own while it runs, which stays a failure as in feature 003; an agent's extended card, which the service never asks for; changing the allowed hosts while the service runs or from the console; patterns that allow several hosts at once; a token that differs per thread, per user, or per request; more than one token per agent; reaching an agent through a proxy; showing or exporting a stored token; and a check that tells whether an agent accepts a token without sending it work.
- This feature specifies Freyja's side only. An agent that is to be reached this way has to listen where the service can reach it and has to say on its card that it asks for a bearer token. Changing such an agent is that agent's own work and is not specified here.
- The console is in English and is used with a current desktop browser, as before.

**Behavior choices**

- The allowed hosts are deployment configuration, not operator-managed configuration (FR-001). The list bounds where the service can be made to connect, by anyone who can reach its unauthenticated API. If it could be changed through that same API, it would bound nothing. The constitution's principle IV already puts addresses and limits a deployment needs before it can start in the environment.
- A host is allowed as written, and names are not looked up to decide (FR-002). The description says the deployment names the hosts. Looking names up would make what is accepted depend on a resolver the service does not control; comparing as written keeps the decision a fixed rule on stored values. The cost is that an allowed name which resolves somewhere unintended is the deployment's to notice.
- Exact hosts only, no patterns (FR-001). A pattern such as every host of a cluster would let anyone who can reach the console point an agent at any service there. A deployment that needs several hosts lists them.
- A token is sent only to an agent whose card asks for one, and the card is read without it (FR-013). The description says the token is never sent to an agent that did not ask for one. An address typed wrongly is then less likely to be handed the token on first contact: whatever answers there would first have to serve a card that asks for one. This lowers the chance of an accident and is not a boundary: anything that controls what answers at an agent's address can obtain the token (Edge Cases). The cost is that an agent which protects even its card cannot be used (FR-016).
- A stored token does not follow its agent to another scheme, host, or port (FR-011). The description lets an operator change an agent and says a token is never shown. If a token followed a move, anyone who can reach the console could move an agent to a listener of their own, approve one hand-off, and be sent the token, which is reading it back by another route. The cost is that an operator who moves an agent enters its token again.
- An allowed host may be listed with a port or without (FR-001). The description says the deployment names hosts. With a port, the entry is one place; without, the deployment accepts every port there. Requiring a port on every entry was considered and not adopted, because a deployment may run several agents on one host; it is the first thing to tighten if the console is ever reachable by more people.
- After an agent refuses its token, the service stops presenting it by itself (FR-017). Watching pending tasks would otherwise present a refused token every round, which an agent may answer by locking the caller out.
- Saving and checking an agent do not tell whether the agent accepts the token (FR-025). Feature 005 lets the service contact an agent by itself only to read its card and a pending task's status, so that adding or checking an agent never hands it work. Whether a token is right is learned at the first request that carries it. A check that verifies a token was considered and left out: it would need a request made only to be refused or accepted.
- An address without encryption is accepted for a remote agent with a token, with a warning (FR-019). Inside one deployment, services often speak to each other without encryption on a network the deployment controls, and an agent may offer nothing else. Refusing would make the feature unusable there; a setting to permit it would be one more thing to configure for the same decision the deployment already made by allowing the host. Requiring an encrypted address for every remote agent was considered and not adopted.
- Certificate verification cannot be turned off, and no certificate authority can be added (FR-018). A deployment whose agents present certificates the machine does not trust has to install its authority on the machine, outside this feature.
- A token change does not read the card and does not give up tasks (FR-010). The agent and its address are the same; only what Freyja presents changes. Feature 005 treats a change of the approval choice the same way. It applies to runs that start afterwards and not to a run in progress, unlike a tightened approval choice in feature 005: the token a run in progress holds goes only to the agent it was entered for, so nothing unseen or misdirected follows from letting the run finish with it.
- A token is at least 16 characters (FR-006), so that the four characters shown are at most a quarter of it. Feature 004 shows nothing of a key shorter than eight characters for the same reason.
- The token is removed from an agent's own replies and progress updates as well as from errors (FR-021). Feature 005 does not search an agent's replies for its address, because the agent may legitimately mention where it is. A token is different: nothing legitimate repeats it, and the party that would is the one that holds it.
- The last four characters of an environment agent's token are shown in the Agents section (FR-020), as feature 004 shows them for the environment's model key. They let an operator tell which token a deployment was given without revealing it.
- Local or remote decides one thing only: whether the address needs an allowed host. A local agent may ask for a token, and a remote agent may ask for none (Edge Cases).
- Trust, as far as it changes. The deployment is trusted to name hosts and to vouch for what their names resolve to and for the network path to them. The operator is trusted as in feature 005, and can now also point a saved agent at any allowed host and give it a token; they can never read a token back, by the console or by moving the agent (FR-011). An agent is trusted with the token it was given and with nothing more: its card decides whether a token is sent, and never where. An agent's card remains untrusted text.

**Earlier requirements this feature replaces**

- Feature 003, FR-001 and FR-003, and feature 005, FR-006 and FR-018, with the scenarios that restate them (005, User Story 2 scenario 7 and User Story 3 scenario 3) and the description of a delegate agent as having an address on this machine: an address that is not local is no longer refused when its host is allowed (FR-002, FR-004).
- Feature 003, FR-003, and feature 005, FR-007 and FR-016: a card that asks for a bearer token no longer makes an agent unusable when a token is configured, a card that describes a kind of credential and requires none no longer does either (FR-012), and the one reason for a card that requires authentication becomes the reasons of FR-016.
- Feature 003, for one case: an environment agent's address that carries a user name or a password is refused when the agent has a token or the address is remote (FR-007).
- Feature 005, FR-006 and FR-028: the comparison of two addresses, and the forms in which an address is removed from text, gain the host for a remote address (FR-005, FR-023).
- Feature 005, its out-of-scope list: agents on another machine and agents that need credentials are now in scope, within the limits above.
- Feature 005, the assumption that instances sharing a database run where the same local addresses reach the same agents: a remote address reaches the same agent from every instance, and the assumption remains for local addresses only.
- Feature 005, the statement of what anyone who can reach the port can do: requesting a card from any port and learning the kind of failure now covers every allowed host listed without a port, beside this machine.

**Environment and dependencies**

- This specification is written as if feature 005 were complete. If feature 005 is finished differently from its specification, this one is read again before it is planned.
- The constitution needs no amendment. Principle II already has agents reached over A2A, which defines how a card declares that it asks for a bearer token. Principle IV already puts what a deployment needs before it can start in the environment, and already requires a secret an operator enters to be stored encrypted under a key from the environment and never returned, logged, or written to a thread; a saved agent's token is such a secret. Principle I is untouched: the approval gate, its decisions, and its rules do not change.
- The secret that protects stored LLM API keys (feature 004) also protects stored tokens. A deployment that never stores a token does not need it for this feature.
- The service's own API stays unauthenticated and is not exposed beyond the service's own machine. With this feature, anyone who can reach it can point a saved agent at any allowed host and present a token to it, in addition to what feature 005 already lets them do. They cannot read a stored token, and they cannot reach a host the deployment did not allow. This must be revisited before the API is exposed more widely, as before.
- Several service instances sharing one database are assumed to all run a version that knows remote addresses and tokens before the first such agent is saved, and to be given the same allowed hosts. What an instance on an earlier version does with such an agent is not specified.
- The stand-in agent of feature 003 plays every agent in the automated tests, extended so that it can ask for a bearer token, refuse one, and repeat one in its answer.
